# 01. AWS インフラ構築（AWS 画面での作業）

この文書では AWS マネジメントコンソール（ブラウザの管理画面）だけを使い、次の5つを順番に作ります。

| Step | 作るもの | なぜ必要か |
|---|---|---|
| 1 | VPC（仮想ネットワーク） | EC2 を置く場所。これが無いと EC2 を建てられない |
| 2 | キーペア（SSH の鍵） | VS Code から SSH 接続するときの本人確認に使う |
| 3 | IAM ロール（SSM 用の許可証） | EC2 が AWS の接続中継サービス（SSM）と通信するための許可 |
| 4 | EC2 インスタンス | 開発サーバー本体。Step 1〜3 の成果物をここで組み合わせる |
| 5 | （接続テスト） | ローカル PC の設定に進む前に、AWS 側だけで接続できることを確認 |
| 6 | 自動停止スケジュール | 毎晩 21:00 に EC2 を止めて課金を止める |

**作業の前に**: コンソールにログインしたら、**画面右上のリージョン表示が「東京」になっていることを確認**してください。違っていたらクリックして「アジアパシフィック（東京）ap-northeast-1」を選びます。ここを間違えると、以降の作業がすべて別の場所に作られます。

---

## Step 1: VPC を作成する

### なぜ必要か

VPC は AWS 内に借りる「自分専用のネットワーク区画」で、EC2 は必ずどこかの VPC の中に置く決まりだからです。AWS には便利なウィザード（「VPC など」という作成モード）があり、ネットワークに必要な部品一式（サブネット・インターネットへの出口・経路表）を1画面でまとめて作れます。手作業で1個ずつ作ると6手順になるところが1手順で済むので、これを使います。

### 操作

1. 画面上部の検索窓に「**VPC**」と入力 → 検索結果の「VPC」をクリック
2. オレンジ色の「**VPC を作成**」ボタンをクリック
3. 以下のとおり設定します（**書いていない項目は初期値のまま触らない**）:

| 項目 | 設定値 | 補足 |
|---|---|---|
| 作成するリソース | **VPC など** | 「VPC のみ」ではない方。部品一式をまとめて作るモード |
| 名前タグの自動生成 | 自動生成にチェックのまま、名前欄に **`dev`** | 作られる部品全部に「dev-」の名前が付く |
| IPv4 CIDR ブロック | **`10.0.0.0/16`**（初期値のまま） | この区画の住所範囲。初期値で問題ない |
| IPv6 CIDR ブロック | **IPv6 CIDR ブロックなし**（初期値のまま） | 使わない |
| テナンシー | **デフォルト**（初期値のまま） | |
| アベイラビリティーゾーン (AZ) の数 | **1** | データセンターの棟数。開発機1台なので1でよい（初期値の2から変更） |
| パブリックサブネットの数 | **1** | インターネットと通信できる部屋を1つ |
| プライベートサブネットの数 | **0** | 使わない（初期値の2から変更）。**ここを0にするのが重要**（プライベートサブネットを作ると次の NAT の話が絡んでくる） |
| NAT ゲートウェイ | **なし** | ⚠️ **絶対に「なし」**。作ると存在するだけで月7千円級の課金が発生する（00 §4 参照） |
| VPC エンドポイント | **なし** | 今回は使わない（初期値が「S3 ゲートウェイ」の場合は「なし」に変更） |
| DNS オプション | 両方チェックのまま | |

4. 右下の「**VPC を作成**」をクリック → 緑のバーで作成の進行が表示され、20秒ほどで完了
5. 「VPC を表示」をクリックし、`dev-vpc` という VPC ができていることを確認

### 確認

- 左メニュー「サブネット」を開くと `dev-subnet-public1-apne1a` のような名前のサブネットが**1つ**あること
- 左メニュー「NAT ゲートウェイ」を開いて**空**であること（もし作ってしまっていたら、選択 →「アクション」→「NAT ゲートウェイを削除」で今すぐ削除。放置すると課金が続く）

## Step 2: キーペア（SSH の鍵）を作成する

### なぜ必要か

VS Code の SSH 接続では、パスワードの代わりに「鍵ファイル」で本人確認をします。ここで鍵のペアを作ると、**公開鍵**（南京錠に相当）は AWS が EC2 に自動で取り付け、**秘密鍵**（その南京錠を開ける鍵・`.pem` ファイル）があなたの PC にダウンロードされます。

> ⚠️ **秘密鍵ファイルは再ダウンロードできません**。作成時の1回しかダウンロード機会がなく、失くしたら鍵を作り直して EC2 に付け替える作業（面倒）になります。ダウンロードされたファイルは消さずに保管してください。

### 操作

1. 検索窓に「**EC2**」と入力 → 「EC2」をクリック
2. 左メニューの「ネットワーク & セキュリティ」→「**キーペア**」をクリック
3. 右上「**キーペアを作成**」をクリック
4. 以下を設定:

| 項目 | 設定値 | 補足 |
|---|---|---|
| 名前 | **`dev-ec2-key`** | |
| キーペアのタイプ | **ED25519** | 新しく強い方式。今回の構成（Windows 標準の SSH）で問題なく使える |
| プライベートキーファイル形式 | **.pem** | OpenSSH（Windows 標準・VS Code が使う）用の形式 |

5. 「**キーペアを作成**」をクリック → `dev-ec2-key.pem` が自動でダウンロードされる（通常は「ダウンロード」フォルダに入る）

### 確認

- PC のダウンロードフォルダに `dev-ec2-key.pem` があること。**このファイルは手順書 02 で使うので、その場に置いたままで OK**（02 で正しい置き場所に移動します）

## Step 3: SSM 接続用の IAM ロールを作成する

### なぜ必要か

EC2 が AWS の接続中継サービス（SSM）に「自分はここにいます、接続を受け付けます」と名乗り出るには、その通信の許可証（IAM ロール）が必要だからです。AWS が用意している既製の許可セット `AmazonSSMManagedInstanceCore` をロールに入れて、EC2 に持たせます。

- 根拠: [AWS 管理ポリシーリファレンス AmazonSSMManagedInstanceCore](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/AmazonSSMManagedInstanceCore.html) — このポリシーは「EC2 インスタンスが Systems Manager のコア機能を使えるようにするためのもの」と説明されています。Session Manager 接続の必要条件です
- **会社メモの「ロールを作って、エンティティを作って、ユースケースとポリシーを…」はこの画面のことです。** 以下の手順の太字がメモの単語に対応します

### 操作

1. 検索窓に「**IAM**」と入力 → 「IAM」をクリック
2. 左メニュー「**ロール**」→ 右上「**ロールを作成**」をクリック
3. 画面1（信頼されたエンティティを選択）:

| 項目 | 設定値 |
|---|---|
| 信頼された**エンティティ**タイプ | **AWS のサービス** |
| **ユースケース**（サービスまたはユースケース） | **EC2** を選択（その下の選択肢は「EC2」のまま） |

4. 「次へ」をクリック
5. 画面2（許可を追加）: 検索窓に「**AmazonSSMManagedInstanceCore**」と入力 → 出てきた**ポリシー**の左のチェックボックスを ON → 「次へ」
6. 画面3（名前、確認、および作成）:

| 項目 | 設定値 |
|---|---|
| ロール名 | **`ec2-ssm-role`** |
| 説明 | そのままで OK |

7. 「**ロールを作成**」をクリック

### 確認

- ロール一覧に `ec2-ssm-role` が表示されること。クリックして「許可」タブに `AmazonSSMManagedInstanceCore` が1つだけ付いていること

## Step 4: EC2 インスタンスを作成する

いよいよ本体です。Step 1〜3 で作った部品をここで全部組み合わせます。設定項目が多いので、**1項目ずつ照合しながら**進めてください。

### 操作

1. 検索窓から「**EC2**」を開く → 左メニュー「インスタンス」→ 右上のオレンジ「**インスタンスを起動**」をクリック
2. 以下のとおり設定します:

**名前とタグ**

| 項目 | 設定値 |
|---|---|
| 名前 | **`dev-ec2`** |

**アプリケーションおよび OS イメージ (AMI)**

| 項目 | 設定値 | 補足 |
|---|---|---|
| クイックスタートの OS | **Ubuntu** | |
| AMI | **Ubuntu Server 24.04 LTS (HVM), SSD Volume Type** | 「24.04 LTS」であることを確認。Pro 版や Minimal 版ではない無印を選ぶ |
| アーキテクチャ | **64 ビット (x86)** | m6a は x86 の CPU なのでこちら。Arm ではない |

> この Ubuntu には SSM 接続に必要なプログラム（SSM Agent）が最初から入っています。根拠: [AWS 公式「SSM Agent がプリインストールされた AMI」](https://docs.aws.amazon.com/systems-manager/latest/userguide/ami-preinstalled-agent.html) — プリインストール済み AMI の一覧に Ubuntu Server 24.04 LTS が明記されています。だから EC2 の中に何かを入れる前から SSM 接続ができます

**インスタンスタイプ**

| 項目 | 設定値 |
|---|---|
| インスタンスタイプ | **m6a.xlarge**（検索窓に「m6a.xlarge」と入力して選択。4 vCPU・16 GiB メモリ） |

**キーペア (ログイン)**

| 項目 | 設定値 |
|---|---|
| キーペア名 | **`dev-ec2-key`**（Step 2 で作ったもの） |

**ネットワーク設定** — 右上の「**編集**」ボタンを押してから設定します（押さないと変更できません）

| 項目 | 設定値 | 補足 |
|---|---|---|
| VPC | **`dev-vpc`** | Step 1 で作ったもの。「vpc-」で始まる ID の横に dev-vpc と表示される |
| サブネット | **`dev-subnet-public1-...`** | public と名の付く方（1つしかないはず） |
| パブリック IP の自動割り当て | **有効化** | EC2 がインターネットに出るため（SSM への名乗り出と、Copilot・パッチ取得に必要） |
| ファイアウォール (セキュリティグループ) | **セキュリティグループを作成する** | |
| セキュリティグループ名・説明 | **`dev-ec2-sg`**（説明欄は自動入力のままで OK） | 初期の自動名のままでも動作に支障はない |
| ⚠️ インバウンドセキュリティグループのルール | **最初から入っている「ssh」のルール（タイプ ssh・ポート 22・ソース 0.0.0.0/0）を「削除」ボタンで消し、ルールを 0 件（空）にする。「ルールを追加」で何かを足す必要も無い** | **ここが重要**。初期状態の ssh ルールを残すと、世界中どこからでも SSH の入口（ポート22）を叩ける状態になる。この構成の接続はすべて SSM 経由（EC2 側から外へ張る通信）なので、**受け入れルールはゼロが完成形**（00 §1 の完成図「外から入る穴（ポート）ゼロ」・00 §2 用語辞典の「受け入れルールを空にする」がこれ） |
| アウトバウンド（外向き）ルール | **何もしない**（この画面には設定欄が出ない。作成されるセキュリティグループには「外向きの通信をすべて許可」の既定ルールが自動で付き、それでよい） | SSM への名乗り出・セキュリティパッチ取得・Copilot はすべて EC2 発の外向き通信。これを消すと何も動かなくなるので、後から触らないこと |

> **「インバウンドルールが空なのに、なぜ SSM や VS Code で繋がるのか」**: セキュリティグループが審査するのは「外から新しく入ってくる通信」だけで、**EC2 側から外へ張った通信への返事は、インバウンドルールに関係なく通る**仕組み（ステートフルと言います）だからです。今回の接続はすべて「EC2 側から SSM へ張った管理回線」（00 §1 の完成図）に相乗りするため、受け入れルール 0 件で成立します。
>
> - 根拠1: [AWS Systems Manager 公式ドキュメント「Session Manager」](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager.html) — 「Session Manager はインバウンドポートを開けたり、踏み台ホストを維持したり、SSH キーを管理したりする必要なしに、安全なノード管理を提供する」「インバウンドの SSH ポートを開けたままにすることは不正なコマンド実行のリスクを大きく高める。Session Manager はこれらのインバウンドポートを閉じることを可能にする」と明記されています
> - 根拠2: [Amazon VPC 公式ドキュメント「セキュリティグループ」](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-security-groups.html) — 「セキュリティグループはステートフルである。インスタンスからリクエストを送信すると、その応答トラフィックは**インバウンドルールに関係なく**インスタンスに到達できる」と明記されています
> - 根拠3: [Amazon VPC 公式ドキュメント「セキュリティグループのルール」](https://docs.aws.amazon.com/vpc/latest/userguide/security-group-rules.html) — 「セキュリティグループの新規作成時点ではインバウンドルールは無く、追加するまでインバウンド通信は一切許可されない」（＝空なら全部門前払い。拒否ルールを書く必要はない）「新規作成時には、すべてのアウトバウンド通信を許可するルールが1つ付く」と明記されています

> 📱 **画面の表示が違う場合**: 「編集」を押す前の要約表示では、ルール一覧の代わりに「**〜からの SSH トラフィックを許可する**」というチェックボックスが出ます（初期状態でチェック ON）。その場合は**チェックを外す**のが同じ意味です（外すとインバウンドルール 0 件で作られる）。どちらの画面から操作しても、目指す完成形は同じ「**インバウンドルール 0 件・アウトバウンドは既定の全許可のまま**」です。

**ストレージを設定**

| 項目 | 設定値 |
|---|---|
| サイズ | **50** GiB |
| ボリュームタイプ | **gp3** |

**高度な詳細** — 折りたたまれているのでクリックして開きます。変更するのは次の2つだけです

| 項目 | 設定値 | 補足 |
|---|---|---|
| IAM インスタンスプロファイル | **`ec2-ssm-role`**（Step 3 で作ったもの） | ⚠️ **忘れると SSM 接続ができない**。この手順書で一番忘れやすいポイント |
| 終了保護 | **有効化** | 「終了（＝削除）」ボタンの誤操作から守る保険（00 §4 参照） |
| 停止保護 | **無効のまま触らない** | ⚠️ 有効にすると毎晩の自動停止が失敗するようになる |

3. 右側の「概要」パネルで内容をざっと確認し、「**インスタンスを起動**」をクリック
4. 「Success」と出たら「**すべてのインスタンスを表示**」をクリック

### 確認

- インスタンス一覧に `dev-ec2` が現れ、「インスタンスの状態」が数分で「**実行中**」になること
- `dev-ec2` の行をクリックして詳細を開き、**「インスタンス ID」（`i-` で始まる17桁前後の文字列）をメモ帳にコピーしておく**。この ID は手順書 02 で2回使います
- 同じ詳細画面の「**セキュリティ**」タブを開き、**インバウンドルールが空**（「インバウンドルールはありません」などの表示・ssh の行が無い）であること。アウトバウンドルールには「すべてのトラフィック」許可が1件あること
  - もし ssh のインバウンドルールが残っていたら（消し忘れて起動した場合）: 「セキュリティ」タブ内のセキュリティグループ名（`sg-` で始まるリンク）をクリック → 「**インバウンドのルールを編集**」→ ssh の行の「**削除**」→「**ルールを保存**」。EC2 を作り直す必要はなく、保存した瞬間から反映されます

## Step 5: AWS 画面から接続テスト（ローカル設定の前の中間チェック）

### なぜやるか

ここで一度、AWS の画面上だけで EC2 に入れることを確かめます。これが通れば「AWS 側の構築（Step 1〜4）は全部正しい」と確定するので、もし手順書 02 で接続に失敗しても、原因をローカル PC 側だけに絞り込めます。

### 操作

1. インスタンス一覧で `dev-ec2` にチェックを入れ、右上の「**接続**」をクリック
2. 「**セッションマネージャー**」タブを選び、「**接続**」をクリック
   - ボタンが押せない場合は5分ほど待ってからページを再読み込みしてください（起動直後は EC2 が SSM に名乗り出る前のことがある）
3. ブラウザ内に黒いターミナル画面が開き、`$` の記号（コマンド待ち受け）が表示されれば成功
4. 試しに `hostname` と入力して Enter → `ip-10-0-…` のような応答が返ることを確認
5. 右上の「終了」でターミナルを閉じる（この「終了」はセッション＝接続を切るだけの意味。**インスタンスの「終了」とは別物**で、EC2 は消えません）

> **ここが動かない場合**: ほぼ確実に Step 4 の「IAM インスタンスプロファイル」の付け忘れです。インスタンスを選択 → 「アクション」→「セキュリティ」→「IAM ロールを変更」→ `ec2-ssm-role` を選んで保存 → 5分待って再挑戦。

## Step 6: 毎晩 21:00 の自動停止を設定する

### なぜ必要か

停止し忘れると、課金が月 ¥7,200 → 約 ¥25,000 に跳ね上がるからです（00 §5）。EventBridge Scheduler という AWS の予約実行サービスに「毎日 21:00（日本時間）に dev-ec2 を停止しろ」という予約を1件仕込みます。

- 根拠: [EventBridge Scheduler 公式ドキュメント「スケジュールタイプ」](https://docs.aws.amazon.com/scheduler/latest/UserGuide/schedule-types.html) — cron 式による定期実行と**タイムゾーン指定**がサポートされていることが書かれています（タイムゾーンを指定できるので、日本時間の 21:00 をそのまま指定でき、時差の計算が不要です）
- 停止先の指定方法の根拠: [同「テンプレート化されたターゲット」](https://docs.aws.amazon.com/scheduler/latest/UserGuide/managing-targets-templated.html) — Scheduler は EC2 の StopInstances（インスタンス停止）を定型ターゲットとして直接呼べると書かれています。プログラムを書かずに画面の選択だけで済むのはこのためです

予約には、Scheduler が EC2 を停止するときに使う機械用の許可証（IAM ロール。画面では「実行ロール」と表示される）を必ず1つ紐付けます。通常は作成画面が自動で用意してくれます。

- 実行ロールが必須である根拠: [同 API リファレンス「Target」](https://docs.aws.amazon.com/scheduler/latest/APIReference/API_Target.html) — 予約の停止先（ターゲット）に紐付ける実行ロール（`RoleArn`）は必須項目（Required: Yes）と明記されています

### 操作

1. 検索窓に「**EventBridge**」と入力 → 「Amazon EventBridge」をクリック
2. 左メニューの「スケジューラ」配下の「**スケジュール**」をクリック → 「**スケジュールを作成**」
3. 画面1（スケジュールの詳細を指定）:

| 項目 | 設定値 | 補足 |
|---|---|---|
| スケジュール名 | **`stop-dev-ec2-2100`** | |
| スケジュールグループ | **default**（初期値のまま） | |
| 頻度（スケジュールのタイプ） | **定期的なスケジュール** | |
| スケジュールの種類 | **cron ベースのスケジュール** | |
| cron 式 | **`cron(0 21 * * ? *)`**（入力欄が分・時・日・月・曜日・年に分かれている場合は 分=`0`、時=`21`、日=`*`、月=`*`、曜日=`?`、年=`*`） | 「毎日 21:00」の意味 |
| タイムゾーン | **(UTC+09:00) Asia/Tokyo** | ⚠️ **初期値は UTC のことがある**。UTC のままだと朝6時に止まる環境になってしまうので必ず東京に変更 |
| フレックスタイムウィンドウ | **オフ** | 「きっかり21:00」に実行させる |

4. 「次へ」
5. 画面2（ターゲットの選択）:

| 項目 | 設定値 | 補足 |
|---|---|---|
| ターゲット API | 「**テンプレート化されたターゲット**」から「**Amazon EC2 StopInstances**」を選択（一覧に無ければ検索窓に「StopInstances」と入力） | |
| InstanceIds | Step 4 でメモした **`i-` で始まるインスタンス ID** | |

6. 「次へ」
7. 画面3（設定）: 基本は初期値のままで OK。次の1点だけ確認:

| 項目 | 設定値 | 補足 |
|---|---|---|
| アクセス許可（実行ロール） | **「このスケジュールに新しいロールを作成」** | Scheduler が EC2 を停止する権限を AWS が自動で用意してくれる。この選択肢が無い画面の場合は、下の**「新しいロールを作成」が選べない場合**の手順でロールを作ってから選ぶ |

8. 「次へ」→ 内容を確認して「**スケジュールを作成**」

### 「新しいロールを作成」が選べない場合

アクセス許可の欄に「既存の役割を選択」しか表示されない画面があります。その場合は、この予約専用の許可証（実行ロール）を IAM で作ってから選びます。Step 3 で作ったロールは EC2 用の許可証なので、ここ専用に新しく作成します。

- 作るロールの根拠: [EventBridge Scheduler 公式ドキュメント「Set up the execution role」](https://docs.aws.amazon.com/scheduler/latest/UserGuide/setting-up.html#setting-up-execution-role) — 手順の中で貼り付ける信頼ポリシーの JSON（サービスに `scheduler.amazonaws.com` を指定）は、ここに公式の例として載っているものです

先に「dev-ec2 を停止してよい」という許可セット（ポリシー）を作ります:

1. 新しいブラウザタブで検索窓に「**IAM**」と入力 → 「IAM」をクリック
2. 左メニュー「**ポリシー**」→ 右上「**ポリシーを作成**」をクリック
3. 「**JSON**」タブをクリック → 入力欄の中身をすべて消して、次を貼り付ける。`i-xxxxxxxxxxxxxxxxx` の部分は Step 4 でメモした自分の**インスタンス ID** に置き換える（「この1台だけ停止できる」という意味になる）:

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": "ec2:StopInstances",
            "Resource": "arn:aws:ec2:ap-northeast-1:*:instance/i-xxxxxxxxxxxxxxxxx"
        }
    ]
}
```

4. 「次へ」をクリック
5. 画面（確認と作成）:

| 項目 | 設定値 |
|---|---|
| ポリシー名 | **`stop-dev-ec2-policy`** |
| 説明 | そのままで OK |

6. 「**ポリシーの作成**」をクリック

次に、このポリシーを持たせたロールを作ります（Step 3 と同じ流れ。エンティティの選び方だけが違います）:

7. 左メニュー「**ロール**」→ 右上「**ロールを作成**」をクリック
8. 画面1（信頼されたエンティティを選択）:

| 項目 | 設定値 |
|---|---|
| 信頼された**エンティティ**タイプ | **カスタム信頼ポリシー**（Step 3 では「AWS のサービス」を選んだが、今回はこちら） |
| カスタム信頼ポリシー（JSON の入力欄） | 中身をすべて消して、下の JSON を貼り付ける（「このロールは Scheduler だけが使える」という宣言） |

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Principal": {
                "Service": "scheduler.amazonaws.com"
            },
            "Action": "sts:AssumeRole"
        }
    ]
}
```

9. 「次へ」をクリック
10. 画面2（許可を追加）: 検索窓に「**stop-dev-ec2-policy**」と入力 → 出てきた**ポリシー**の左のチェックボックスを ON → 「次へ」
11. 画面3（名前、確認、および作成）:

| 項目 | 設定値 |
|---|---|
| ロール名 | **`scheduler-stop-dev-ec2-role`** |
| 説明 | そのままで OK |

12. 「**ロールを作成**」をクリック
13. EventBridge のタブへ戻り、「既存の役割を選択」の欄にある**更新ボタン**をクリック → 一覧から **`scheduler-stop-dev-ec2-role`** を選択 → 上の操作 8（「次へ」→「スケジュールを作成」）に戻る

### 確認

- スケジュール一覧に `stop-dev-ec2-2100` が「有効」で表示されること
- **実運用での最終確認**: 翌日以降、21:00 を過ぎたあとに EC2 のインスタンス一覧を見て「停止済み」になっていること（構築当日に見られればその日に確認）

> **21:00 以降も作業していた日はどうなる？**: 21:00 になると EC2 が容赦なくシャットダウンされ、VS Code の接続が切れます。ただし**保存済みのファイルは消えません**（停止はシャットダウンと同じ・00 §4）。続きをやりたければ、手順書 02 で作る起動スクリプトを実行して再接続するだけです。VS Code は初期設定でファイルを自動保存しないので、**こまめな Ctrl+S の習慣**、または VS Code の自動保存設定（ファイル → 自動保存にチェック）をおすすめします。
