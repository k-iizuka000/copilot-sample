# 03. EC2 内の環境構築（VS Code のターミナルでの作業）

この文書では EC2 の中身を開発できる状態に仕上げます。**作業場所はすべて「dev-ec2 に接続した VS Code のターミナル」**です（メニュー「ターミナル」→「新しいターミナル」。プロンプトが `ubuntu@ip-…$` になっていることを確認。手順書 02 Step 7 参照）。ただし Step 5 と Step 6 の一部だけは会社 PC 側の PowerShell を使います（その場で明記します)。

| Step | やること |
|---|---|
| 1 | 初回アップデートとタイムゾーン設定 |
| 2 | セキュリティパッチの自動適用を確認する |
| 3 | Git を入れる |
| 4 | Java を入れる |
| 5 | 会社のコードを持ち込む（リポジトリ丸ごとコピー） |
| 6 | GitBucket へ変更を返す経路を作る |
| 7 | VS Code の拡張機能と GitHub Copilot を入れ、Java の設定をする |

> **AWS CLI を EC2 に入れない理由**: 当初の想定に「EC2 に AWS CLI を導入」がありましたが、**不要なので入れません**。AWS の操作（起動・停止・設定変更）はすべてローカル PC 側と AWS 画面から行い、EC2 は「開発作業だけをする場所」に保ちます。道具を減らすほど、管理・セキュリティ両面でシンプルになります。

> **コマンド実行の作法**: `sudo` で始まるコマンドは「管理者として実行」の意味です。途中で `[Y/n]` と聞かれたら `y` + Enter、紫やピンクの全画面の確認（サービス再起動の問い合わせ等）が出たら Enter でそのまま進めて OK です。

## Step 1: 初回アップデートとタイムゾーン設定

### なぜやるか

AMI（OS のひな型）は作成時点のパッケージで固まっているため、最初に一度、全体を最新化します。あわせて時計を日本時間にします（初期は UTC で、ログの時刻が9時間ずれて読みにくいため）。

### 操作

```bash
sudo apt update && sudo apt upgrade -y
sudo timedatectl set-timezone Asia/Tokyo
```

- 1行目: パッケージ一覧の更新（update）と、更新があるものの一括適用（upgrade）。初回は数分かかります
- 2行目: タイムゾーンを東京に

### 確認

```bash
date
```

- 日本の現在時刻（JST）が表示されれば OK

## Step 2: セキュリティパッチの自動適用を確認する

### なぜ「設定」ではなく「確認」なのか

Ubuntu Server には `unattended-upgrades` という自動更新の仕組みが**最初から入っていて、セキュリティ更新は既定で自動適用**されるからです。新しく何かを設定する必要はなく、「既定で有効になっていること」を自分の目で確認すれば要件（定期セキュリティパッチ）は満たせます。

- 根拠: [Ubuntu Server 公式ドキュメント「Automatic updates」](https://documentation.ubuntu.com/server/how-to/software/automatic-updates/) — Ubuntu では unattended-upgrades パッケージにより「セキュリティアップデートを自動的にインストールする動作が既定」であることが説明されています

### 操作

```bash
apt-config dump APT::Periodic
systemctl is-active apt-daily.timer apt-daily-upgrade.timer
```

### 確認

- 1つ目が次の2行を含むこと:

```
APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Unattended-Upgrade "1";
```

- 意味: 「毎日パッケージ一覧を更新し（1行目）、毎日、未適用のセキュリティ更新を自動インストールする（2行目）」。`"1"` は有効の意味です
- 2つ目が **`active` を2行**返すこと。この2つのタイマーが毎日決まった時刻に起動し、上の設定値を読んで更新を実行します。設定値とタイマーの両方がそろって初めて「自動で当たっている」状態です
  - 根拠: [Ubuntu 公式マニュアル `unattended-upgrade(8)`](https://manpages.ubuntu.com/manpages/noble/man8/unattended-upgrade.8.html) — 「`APT::Periodic::Unattended-Upgrade` オプションのバックエンドであり、APT の systemd サービス（`apt-daily-upgrade.service`）から定期実行される」と記載されています

> **設定ファイルを直接 `cat` しない理由**: 値の実体は `/etc/apt/apt.conf.d/20auto-upgrades` にありますが、このファイルはパッケージに同梱されておらず、導入時に生成されるものです（[パッケージのファイル一覧](https://packages.ubuntu.com/noble/all/unattended-upgrades/filelist)にこのパスは含まれず、雛形が `/usr/share/unattended-upgrades/` に置かれているだけです）。そのため AMI によっては存在しなかったり、別のファイルに書かれていたりします。`apt-config dump` は設定ファイル群を読んだ**最終的な実効値**を表示するので、ファイル名に左右されずに判定できます。

> **`systemctl is-enabled unattended-upgrades` は判定に使えません**: 同名のサービスは存在しますが、その正体は「Unattended Upgrades Shutdown」＝**シャットダウン時に更新の完了を待つ**ためのもので、`enabled` と返っても毎日の自動更新が動いている証拠にはなりません。判定は上の2コマンドで行ってください。

> **`No such file or directory` や `syntax error` が出たときは**: まずコマンドの打ち間違いを疑ってください。手順書からコピーして貼り付けるとき、経路によっては引用符が別の記号（バッククォート等）に置き換わったり、パスが欠けたりします。ファイルの実在は `ls /etc/apt/apt.conf.d/` で確認できます。**「ファイルが無い」と判断する前に、この確認を挟んでください**

- 補足: カーネル（OS の芯）の更新だけは再起動しないと効きません。**月1回くらい、朝の起動直後に `sudo reboot` を実行**する習慣にしておくと万全です（1〜2分で立ち上がり、VS Code は再接続すれば戻ります。04 にも記載）

## Step 3: Git を入れる

### なぜ必要か

持ち込むコードは Git リポジトリ（履歴付き）なので、EC2 上でコミットや履歴の確認をするのに必要です。あわせて、リソース使用状況を見る道具 `htop`（04 で使う）も入れておきます。

### 操作

```bash
sudo apt install -y git htop
git config --global user.name "あなたの名前"
git config --global user.email "あなたのメールアドレス"
```

- 2〜3行目: コミットに記録される名前とメールアドレス。**GitBucket でいま使っているものと同じ値**にしてください（会社 PC の PowerShell で `git config user.name` と `git config user.email` を実行すると現在値が見られます）

### 確認

```bash
git --version
git config --global --list
```

- バージョンと、設定した name / email が表示されれば OK

## Step 4: Java を入れる

### 事前確認: 案件の Java バージョン

**プロジェクトの `pom.xml`（Maven の場合）の `<java.version>` が正**です。会社 PC で `pom.xml` を開いて確認してください。

```xml
<java.version>1.8</java.version>
<spring.boot.version>2.4.13</spring.boot.version>
```

- **`1.8` は Java 8 のことです**（Java 8 までは `1.x` という表記でした）。`17` なら Java 17、`21` なら Java 21
- `<java.version>` が見当たらない場合は `<maven.compiler.source>` を見ます。どちらも無ければ案件のリーダーに確認してください
- 会社 PC の PowerShell で `java -version` を実行して調べる方法もありますが、**PC に入っている Java と案件が使う Java は別物のことがある**ので、`pom.xml` を優先してください

> **「新しい Java を入れておけば安心」ではありません**: 古い Spring Boot は新しい Java では動きません。例えば Spring Boot 2.4 系は「**Java 8 が必要で、Java 16 まで互換**」と定められており、Java 17 以降は対象外です。根拠: [Spring Boot 2.4 公式ドキュメント「System Requirements」](https://docs.spring.io/spring-boot/docs/2.4.x/reference/html/getting-started.html) — 「Spring Boot 2.4.13 requires Java 8 and is compatible up to Java 16 (included)」と明記されています。**会社 PC で動いているものと同じバージョンを入れる**のが原則です。

### 操作（EC2 側）

案件のバージョンに合わせて、次のどれか1行だけを実行します。

Java 8（`1.8`）の場合:

```bash
sudo apt install -y openjdk-8-jdk
```

Java 17 の場合:

```bash
sudo apt install -y openjdk-17-jdk
```

Java 21 の場合:

```bash
sudo apt install -y openjdk-21-jdk
```

ビルドツールについて:

- プロジェクトのフォルダ直下に `mvnw` や `gradlew` というファイルがある場合（Wrapper 方式）、**ビルドツールのインストールは不要**です。`./mvnw` / `./gradlew` がツール本体を自動で取ってきます
- 無い場合で Maven プロジェクト（`pom.xml` がある）なら: `sudo apt install -y maven`

> **Maven を入れたら `java -version` をもう一度確認してください**: `maven` パッケージは別のバージョンの Java を道連れで入れることがあり、既定の Java が入れ替わる場合があります。案件のバージョンと違っていたら `sudo update-alternatives --config java` で選び直せます（一覧の番号を入力して Enter）。

### 確認

```bash
java -version
```

- 意図したバージョンが表示されれば OK です（Java 8 の場合は `openjdk version "1.8.0_xxx"` の形で表示されます）

## Step 5: 会社のコードを持ち込む（リポジトリ丸ごとコピー）

### 考え方（なぜ「コピー」で安全なのか）

会社の GitBucket は社内ネットワークにあり、EC2 から直接届かない前提です（会社の「ソースはコピーして持っていけば良い」はこのため）。そこで、**会社 PC にある clone 済みリポジトリをフォルダごと EC2 に送ります**。リポジトリのフォルダには `.git` という隠しフォルダ（履歴・ブランチの本体）が含まれているので、**フォルダコピー＝ Git の履歴ごと引っ越し**です。ファイルを1個ずつコピペするのとは違い、何も失われません。

> **どちらで打つコマンドかを、プロンプトで見分けてください**: この Step は会社 PC と EC2 を行き来します。打つ前に、ターミナルの行頭がどちらなのか確認してください。
>
> - `PS C:\Users\…>` → **会社 PC の PowerShell**
> - `ubuntu@ip-10-0-0-0:~$` → **EC2**（VS Code のターミナル）
>
> 場所を間違えると `Could not resolve hostname …`（接続先が分からない）というエラーになります。コマンドが間違っているのではなく、打つ場所が違うだけです。

### 操作（会社 PC の PowerShell で実行）

1. EC2 側に置き場所を作る:

```powershell
ssh dev-ec2 "mkdir -p ~/work"
```

2. リポジトリを1つのファイルにまとめる（`C:\path\to` は clone フォルダの**1つ上**のパスに置き換え。エクスプローラーでフォルダを右クリック →「パスのコピー」が楽です）:

```powershell
cd "C:\path\to"
tar -czf repo.tar.gz リポジトリ名
```

3. まとめた1ファイルを転送する:

```powershell
scp repo.tar.gz dev-ec2:work/
```

> **フォルダのまま `scp -r` で送らない理由**: `scp` は**ファイル1個ごとに通信の往復**が発生します。Java プロジェクトは `.git`（履歴の本体）を含めるとファイル数が数千〜数万になることがあり、SSM トンネル経由では1ファイルあたり1秒前後かかって、数時間コースになります。1つのファイルにまとめてしまえば往復は1回で済み、数分で終わります。根拠: [OpenSSH 8.0 リリースノート](https://www.openssh.com/txt/release-8.0) — 「The scp protocol is outdated, inflexible and not readily fixed」として、OpenSSH 自身が scp の利用を推奨していません。

- `tar` は Windows 10 以降に標準で入っています（`tar --version` で確認できます）
- ビルド成果物を除くと、さらに小さく速くなります: `tar -czf repo.tar.gz --exclude=target リポジトリ名`
- ファイル数が気になるときは `(Get-ChildItem -Recurse -Force -File "C:\path\to\リポジトリ名").Count` で数えられます（`-Force` が無いと `.git` の中が数から漏れます）

### 操作（EC2 側・VS Code のターミナルで実行）

4. 送ったファイルを展開する:

```bash
cd ~/work
tar -xzf repo.tar.gz
rm repo.tar.gz
ls
```

- `ls` でリポジトリ名のフォルダが見えれば転送成功です

5. 改行コードの調整をします。**Windows と Linux ではテキストの改行の記号が違う**ため、Windows から持ち込んだ直後の状態では「全ファイルが変更された」と Git が誤解することがあります。次の設定で正しく比較されるようになります:

```bash
cd ~/work/リポジトリ名
git config core.autocrlf input
git status
```

### 確認

- `git status` の結果が `nothing to commit, working tree clean`（変更なし）になること。※数ファイルだけ変更と出る場合、それは持ち込み前から本当に変更していたファイルなので問題ありません
- `git log --oneline -5` で見覚えのあるコミット履歴が表示されること（履歴ごと持ち込めた証拠）

### VS Code でこのフォルダを開く

メニュー「ファイル」→「フォルダーを開く」→ `/home/ubuntu/work/リポジトリ名` を選択 → 「OK」。以降の開発はこの画面で行います（信頼するかの確認が出たら「はい、作成者を信頼します」）。

## Step 6: GitBucket へ変更を返す経路を作る

### 考え方

会社の GitBucket は社内ネットワークにあり、EC2 からは**そのままでは届きません**。返し方は2通りあります。

```
方法A: [EC2] git push ─▶ 自分の 8048 番 ─(会社 PC との SSH 接続に相乗り)─▶ [会社 PC] ─▶ [GitBucket]

方法B: [EC2 のリポジトリ] ─(1) git pull で取り込む─▶ [会社 PC のリポジトリ] ─(2) git push─▶ [GitBucket]
          （普段の開発・コミットはここ）                    （中継役）                （会社の正）
```

- **方法A（おすすめ）**: 設定は初回だけ。以降は EC2 で `git push` するだけで済みます
- **方法B**: 方法A が会社の方針で使えない場合。push のたびに会社 PC で2コマンド実行します

> **どちらを使うにせよ、事前に会社の方針を確認してください**: 方法A は「AWS 上の EC2 から社内システムへ届く状態」を作ります。通信は会社 PC が張っている既存の SSH 接続の中だけを通り、社内サーバーが社外へ公開されるわけではありませんが、判断は IT 部門か案件のリーダーに確認してから進めてください。

---

### 方法A: EC2 から直接 push する

準備は2つ、**会社 PC で1つ・EC2 で1つ**です。両方そろって初めて通ります。片方だけでは動かないので、続けて実施してください。

#### 準備の前に: GitBucket のホスト名とポートを控える

普段ブラウザで GitBucket を開いたときの URL を見てください（`pom.xml` の `<scm>` に書いてあるものでも同じです）。

```
http://dev-gitbucket.example.co.jp:8048/gitbucket/team/myproject.git
       └────── ホスト名 ──────┘└ポート┘
```

この2つを、以下の手順に出てくる `GitBucketのホスト名` と `8048` に読み替えて使います。

#### 準備1【会社 PC で作業】SSH 設定に通り道を1行足す

1. VS Code で F1 キー →「**Remote-SSH: Open SSH Configuration File...**」→ `C:\Users\ユーザー名\.ssh\config` を選ぶ（メモ帳で直接開いても構いません）
2. 02 で作った EC2 用の `Host` の固まりを探す
3. **その固まりの一番下**に1行足して保存する。行頭の空白は他の行と揃えてください

足す前:

```
Host dev-ec2
    HostName i-0123456789abcdef0
    User ubuntu
    IdentityFile C:\Users\ユーザー名\.ssh\dev-ec2-key.pem
    ProxyCommand （02 で設定したもの）
```

足した後（最後の1行が追加分）:

```
Host dev-ec2
    HostName i-0123456789abcdef0
    User ubuntu
    IdentityFile C:\Users\ユーザー名\.ssh\dev-ec2-key.pem
    ProxyCommand （02 で設定したもの）
    RemoteForward 8048 GitBucketのホスト名:8048
```

- 意味: 「**EC2 側の 8048 番への通信を、会社 PC を経由して社内 GitBucket へ流す**」。左の数字が EC2 側で開く番号、右が実際の宛先です。**左右を同じ番号にしておく**と、あとでリポジトリの URL を書き換えずに済みます
- この待ち受けは **EC2 自身（localhost）にだけ**開きます。EC2 の外から入れるポートが増えることはありません。根拠: [OpenSSH `ssh_config` マニュアル](https://man.openbsd.org/ssh_config#RemoteForward) — 「bind_address を指定しない場合、既定ではループバックアドレスにのみバインドする」と記載されています

4. **VS Code の接続を切って繋ぎ直す**（左下の「><」→「**Close Remote Connection**」→ もう一度 `dev-ec2` に接続）
   - この設定は**接続するときに読まれる**ので、繋ぎ直さないと効きません。ここを飛ばすと次の確認で失敗します

#### 準備2【EC2 で作業】ホスト名の向き先を自分自身にする

EC2 の VS Code のターミナル（プロンプトが `ubuntu@ip-…$` の画面）で、1回だけ実行します。

```bash
echo "127.0.0.1 GitBucketのホスト名" | sudo tee -a /etc/hosts
```

- **正解の見え方**: 実行すると、いま追加した行（`127.0.0.1 GitBucketのホスト名`）がそのまま画面に表示されます。それが成功の合図です
- 意味: 「EC2 の中では、GitBucket のホスト名を自分自身（＝準備1 で開いた通り道の入口）として扱う」
- これで**リポジトリの設定を書き換えずに**、会社 PC と同じ URL のまま push できます

#### 開通確認【EC2 で作業】

準備1・2 が両方効いているかを、push する前にまとめて確かめます。

```bash
cd ~/work/リポジトリ名
git ls-remote origin
```

- **正解**: GitBucket のユーザー名とパスワードを聞かれ、入力すると**ブランチの一覧（英数字の羅列とブランチ名）が表示される**。これで通り道と認証の両方が確認できます
- うまくいかないときは:

| 表示されたもの | 原因と対処 |
|---|---|
| `Connection refused` | 準備1 が効いていません。VS Code を繋ぎ直したか、`config` に足した行の行頭の空白が他の行と揃っているかを確認 |
| `Could not resolve host` | 準備2 のホスト名の打ち間違いです。`tail -1 /etc/hosts` で追加した行を見直してください |
| ユーザー名・パスワードを何度も聞かれる | 下の `credential.helper` の設定を入れてください |

#### 毎回の返し方【EC2 で作業】

```bash
git push origin ブランチ名
```

- 会社 PC でやるのと同じコマンドです
- **パスワードを EC2 に平文で保存しないでください**（`credential.helper store` は使わない）。毎回入力するか、一定時間だけメモリに覚えさせる次の設定にします:

```bash
git config --global credential.helper 'cache --timeout=3600'
```

- **VS Code で EC2 に繋いでいる間だけ使えます**。接続していないときの push は `Connection refused` になります（異常ではありません。繋ぎ直せば通ります）

### 方法B: 会社 PC を中継する

Git は SSH 経由で他のマシンのリポジトリと直接やり取りできるので、会社 PC から見て「EC2 上のリポジトリ」をリモート（取り込み元）として登録します。

#### 初回だけの準備【会社 PC で作業】（PowerShell で実行）

1. Git が使う SSH を Windows 標準のものに固定します（Git は自前の SSH を使うことがあり、それだと手順書 02 の SSM トンネル設定を読めないため。この1行で VS Code と同じ SSH を使うようになります）:

```powershell
git config --global core.sshCommand "C:/Windows/System32/OpenSSH/ssh.exe"
```

2. 会社 PC の clone フォルダに移動し、EC2 を取り込み元として登録します（パスとリポジトリ名は実際のものに置き換え）:

```powershell
cd "C:\path\to\リポジトリ名"
git remote add ec2 dev-ec2:work/リポジトリ名
```

#### 毎回の返し方【会社 PC で作業】（PowerShell で・push したいときだけ）

```powershell
cd "C:\path\to\リポジトリ名"
git pull ec2 ブランチ名
git push origin ブランチ名
```

- 1行目: EC2 での作業内容（コミット）を会社 PC に取り込む
- 2行目: それを GitBucket（origin）へ送る
- `ブランチ名` は普段作業しているブランチ（例: `main`、`develop`、`feature/xxx`）に置き換えてください

#### 確認【会社 PC で作業】

- `git pull ec2 ブランチ名` の後、会社 PC で `git log --oneline -3` を実行すると、EC2 で行ったコミットが先頭に見えること
- GitBucket の画面でそのコミットが見えること

> **会社のコードを GitHub へ push しないでください**: EC2 からは GitHub には届きます（Copilot が動いているのはこのため）。しかしコードの正は会社の GitBucket です。持ち出し先を増やすことになるので、**社外のリポジトリサービスへは上げない**でください。EC2 から返す先は、上の方法A または方法B で繋がる GitBucket だけです。

## Step 7: VS Code の拡張機能と GitHub Copilot を入れ、Java の設定をする

### 考え方

Remote-SSH 接続中の拡張機能には「ローカル側に入れるもの」と「**EC2 側に入れるもの**」の2種類があります。コードを扱う拡張（Java、Copilot）は EC2 側に入れます。といっても操作は普通のインストールと同じで、接続中に入れると VS Code が自動で EC2 側に配置してくれます。

### 操作（dev-ec2 に接続した VS Code で）

1. 左端の拡張機能アイコンをクリック
2. 「**Extension Pack for Java**」を検索 → 「インストール」をクリック
   - ボタンが「SSH: dev-ec2 にインストール」という表記の場合もそのままクリック（同じ意味です）
   - これは Microsoft 製の Java 拡張セット（言語サーバー・デバッガ・Maven 対応等）です
3. 「**GitHub Copilot**」を検索 → 同様にインストール
4. インストール後、右下または左下に「**サインイン**」を促す表示が出ます。「GitHub にサインインする」をクリック → ブラウザが開く → **会社支給の（Copilot が有効な）GitHub アカウント**でログイン → 「Authorize Visual-Studio-Code」の緑ボタンをクリック → VS Code に戻る

### プロジェクトの Java バージョンを VS Code に教える（案件が Java 17 未満なら必須）

Java 拡張の本体（コードを解析する「言語サーバー」）は、新しい Java の上で動く作りになっています。放っておくとプロジェクトも新しい Java 前提で解析されるため、**Java 8 の案件では正しいコードに赤波線が出ます**。Step 4 で入れた JDK を使うよう、次の設定を1回だけ入れます。

1. VS Code で開いているプロジェクトのフォルダ（`~/work/リポジトリ名`）の中に `.vscode` フォルダを作り、その中に `settings.json` を作る
   - 左のエクスプローラーでフォルダ名の横の「新しいフォルダー」→ `.vscode` → その中に「新しいファイル」→ `settings.json`
2. 次の内容を貼り付けて保存する（Java 8 の場合）:

```json
{
  "java.configuration.runtimes": [
    {
      "name": "JavaSE-1.8",
      "path": "/usr/lib/jvm/java-8-openjdk-amd64",
      "default": true
    }
  ]
}
```

- `name` はバージョンの呼び名です。Java 8 は **`JavaSE-1.8`**、Java 17 は `JavaSE-17`、Java 21 は `JavaSE-21`
- `path` は Step 4 で入れた JDK の場所です。ターミナルで `ls /usr/lib/jvm/` を実行すると実際のフォルダ名が確認できます（Java 17 なら `java-17-openjdk-amd64` のような名前になります）
- 根拠: [Java 拡張（Red Hat）公式 README](https://github.com/redhat-developer/vscode-java) — `java.configuration.runtimes` に「実行環境の名前」と「JDK の場所」の対応を並べる設定方法と、`JavaSE-1.8` を指定する例が記載されています
- 保存したら F1 →「**Java: Clean Java Language Server Workspace**」→ 確認ダイアログで「再起動して削除」を選ぶと、解析がやり直されて設定が反映されます（初回解析と同じく数分かかります）

> **`.vscode/settings.json` はリポジトリに入れるべきか**: このファイルは EC2 のパス（`/usr/lib/jvm/...`）を含むため、会社 PC では意味を持ちません。**GitBucket へは返さない**でおくのが無難です（`git status` に出てきたら、コミットに含めないよう選んでください）。

### 確認

- 右下のステータスバーに Copilot のアイコンが出て、斜線（無効マーク）が付いていないこと
- 適当な `.java` ファイルを開いてコードを書き始めると、薄いグレーの補完提案が表示されること（Tab キーで採用）
- Step 5 で開いたプロジェクトで、`.java` ファイルを開いたときに補完・エラー表示が効くこと（初回は言語サーバーの解析が数分走ります。画面右下の進行表示が落ち着くまで待ってください。**この解析が EC2 の 4コアで走ることこそ、今回の引っ越しの目的**です）
