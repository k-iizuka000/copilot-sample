# 02. ローカル PC の設定（会社 PC・Windows での作業）

この文書では会社の Windows PC に接続用の道具を入れ、VS Code から EC2 に入れるところまでを作ります。

| Step | やること | なぜ必要か |
|---|---|---|
| 1 | AWS CLI のインストール | PC から AWS をコマンド操作する道具。SSM トンネルと起動スクリプトの土台 |
| 2 | アクセスキーの作成と設定 | AWS CLI が「あなた本人の操作」だと証明するための鍵 |
| 3 | Session Manager plugin のインストール | SSM トンネルを PC 側で開く部品 |
| 4 | 秘密鍵ファイルの配置 | SSH の本人確認用の鍵を正しい場所・正しい権限で置く |
| 5 | SSH 設定ファイルの作成 | 「dev-ec2 と言ったら SSM 経由であの EC2 に繋げ」という定義 |
| 6 | 接続テスト（コマンド） | VS Code の前に、土台の SSH が通ることを確認 |
| 7 | VS Code Remote-SSH で接続 | 本命。VS Code の画面が EC2 の中を向く |
| 8 | 起動・停止スクリプトの作成 | 毎朝ダブルクリック1発で EC2 を起動するため |

**PowerShell の開き方**（この文書で何度も使います）: スタートボタンを右クリック →「ターミナル」または「Windows PowerShell」をクリック。黒い（または青い）文字入力画面が開きます。コマンドは1行ずつコピーして貼り付け、Enter で実行してください。

> **社内プロキシについて**: 会社のネットワークによっては、外部への通信が「プロキシ」という関所を通る設定になっていることがあります。**Step 2 の動作確認が成功すればプロキシの心配は不要**です（関所が無いか、あっても素通りできている）。失敗した場合だけ、この文書の最後の「付録: プロキシ設定」を見てください。

## Step 1: AWS CLI をインストールする

### なぜ必要か

SSM のトンネル接続は「AWS CLI が土台、Session Manager plugin が追加部品」という2段構えで動くからです。また、毎朝の起動スクリプト（Step 8）も AWS CLI のコマンドを使います。

- 根拠: [AWS CLI 公式インストールガイド](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html) — Windows 用は MSI インストーラー（下記 URL）で入れると案内されています

### 操作

1. ブラウザで次の URL を開く（そのままダウンロードが始まります）:
   **https://awscli.amazonaws.com/AWSCLIV2.msi**
2. ダウンロードした `AWSCLIV2.msi` をダブルクリック → セットアップ画面はすべて「Next」→ 最後に「Install」→「Finish」（設定変更は一切不要）
3. **PowerShell を開き直して**（インストール前から開いていた画面では認識されません）、次を実行:

```powershell
aws --version
```

### 確認

- `aws-cli/2.x.x Python/...` のようなバージョン表示が出れば成功
- 「aws という用語は認識されません」と出たら: PowerShell を全部閉じてから開き直す → それでもダメなら PC を再起動

---

## Step 2: アクセスキーを作成して AWS CLI に設定する

### なぜ必要か

AWS CLI は「誰の操作か」を証明する鍵が無いと何もできません。その鍵が**アクセスキー**（2つの文字列のペア）で、AWS の画面で発行し、PC に登録します。

> 🔴 **アクセスキーはあなたの管理者権限そのものです**。この2つの文字列を知っている人は誰でも、世界中どこからでもあなたとして AWS を操作できます。**メール・チャットに貼らない、Git にコミットしない、ファイル共有に置かない**。漏れた疑いがあれば即座に無効化します（無効化の方法もこの Step の最後に書いておきます）。

### 操作（AWS 画面側）

1. AWS マネジメントコンソールで検索窓に「**IAM**」→ IAM を開く
2. 左メニュー「**ユーザー**」→ 自分のユーザー名をクリック
3. 「**セキュリティ認証情報**」タブ →「アクセスキー」の欄の「**アクセスキーを作成**」
4. ユースケースの選択画面: 「**コマンドラインインターフェイス (CLI)**」を選択 → 下部の確認チェックボックスに同意のチェック → 「次へ」
5. 説明タグ: 空欄のままで OK →「**アクセスキーを作成**」
6. **この画面に表示される2つの値を控えます**:
   - **アクセスキー**（`AKIA` で始まる20文字）
   - **シークレットアクセスキー**（「表示」を押すと見える長い文字列）— ⚠️ **この画面を閉じると二度と表示できません**。「.csv ファイルをダウンロード」を押して保存しておくのが安全です
7. 「完了」で閉じる

### 操作（PC 側）

PowerShell で次を実行します:

```powershell
aws configure
```

4つ順番に聞かれるので、次のとおり入力して Enter していきます:

| 質問 | 入力する値 |
|---|---|
| AWS Access Key ID | 控えた**アクセスキー**（AKIA...） |
| AWS Secret Access Key | 控えた**シークレットアクセスキー** |
| Default region name | **`ap-northeast-1`**（東京。ここを設定しておくと以降のコマンドで東京指定を省略できる） |
| Default output format | **`json`** |

### 確認

```powershell
aws sts get-caller-identity
```

- 自分のアカウント ID とユーザー名を含む応答（`"Arn": "arn:aws:iam::…:user/あなたの名前"`）が返れば成功。**これは「PC → インターネット → AWS」の経路と鍵の両方が正しい証明**です
- エラーになる場合: 入力ミスなら `aws configure` をもう一度実行すれば上書きできます。ネットワークのエラーっぽいメッセージ（timeout / proxy など）なら文末の「付録: プロキシ設定」へ

> **漏洩時の無効化手順**（覚えておく）: IAM → ユーザー → 自分 → セキュリティ認証情報 → 該当のアクセスキーの「アクション」→「無効化」→「削除」。新しいキーを作り直して `aws configure` をやり直せば復旧です。

## Step 3: Session Manager plugin をインストールする

### なぜ必要か

AWS CLI 単体では SSM のトンネル（接続の土管）を PC 側で開けず、この追加部品が必要だからです。

- 根拠: [AWS 公式「Session Manager plugin をインストールする」](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-working-with-install-plugin.html) — 「AWS CLI でセッションを開始・終了するには Session Manager plugin のインストールが必要」と明記され、Windows 用インストーラーの URL が案内されています

### 操作

1. ブラウザで次の URL を開く（ダウンロードが始まります）:
   **https://s3.amazonaws.com/session-manager-downloads/plugin/latest/windows/SessionManagerPluginSetup.exe**
2. ダウンロードしたファイルをダブルクリックし、すべて既定値のままインストール
3. PowerShell を**開き直して**、次を実行:

```powershell
session-manager-plugin
```

### 確認

- `The Session Manager plugin was installed successfully.` と表示されれば成功

## Step 4: 秘密鍵ファイルを配置する

### なぜ必要か

手順書 01 Step 2 でダウンロードした `dev-ec2-key.pem`（秘密鍵）を、SSH の決まりに合う場所と権限で置くためです。Windows の SSH は「他のユーザーからも読める場所にある秘密鍵」を安全でないとみなして**使用を拒否する**ので、権限の設定までがセットです。

### 操作

PowerShell で次を1行ずつ実行します（1行目: 置き場所フォルダの作成、2行目: ダウンロードフォルダからの移動、3〜4行目: 自分だけが読める権限に変更）:

```powershell
New-Item -ItemType Directory -Force "$env:USERPROFILE\.ssh"
Move-Item "$env:USERPROFILE\Downloads\dev-ec2-key.pem" "$env:USERPROFILE\.ssh\dev-ec2-key.pem"
icacls "$env:USERPROFILE\.ssh\dev-ec2-key.pem" /inheritance:r
icacls "$env:USERPROFILE\.ssh\dev-ec2-key.pem" /grant:r "$env:USERNAME`:R"
```

> 2行目でエラーが出る場合は、`.pem` ファイルがダウンロードフォルダ以外にあるだけです。エクスプローラーで `dev-ec2-key.pem` を探し、`C:\Users\<あなたのユーザー名>\.ssh\` フォルダへ手で移動してから、3〜4行目だけ実行してください。

### 確認

```powershell
icacls "$env:USERPROFILE\.ssh\dev-ec2-key.pem"
```

- 表示される行に**自分のユーザー名だけ**が出てくれば成功（`BUILTIN\Administrators` や `Everyone` が出てこないこと）

## Step 5: SSH 設定ファイルを作成する

### なぜ必要か

「`dev-ec2` という名前に接続しようとしたら、SSM のトンネルを掘って、あの EC2 に、この鍵で入れ」という一連の指示を SSH の設定ファイルに書いておくためです。これを書いておくと、VS Code もコマンドも `dev-ec2` の一言で接続できるようになります。

- 根拠: [AWS 公式「セッションを開始する（SSH 接続）」](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-working-with-sessions-start.html) — SSH 設定ファイルに ProxyCommand（接続の前処理として SSM セッションを開くコマンド）を追記する、という下記そのままの方法が公式手順として記載されています

### 操作

1. PowerShell で次を実行してメモ帳を開きます（「ファイルが見つかりません。新規作成しますか？」と聞かれたら「**はい**」）:

```powershell
notepad "$env:USERPROFILE\.ssh\config"
```

2. 開いたメモ帳に以下を貼り付けます。**1箇所だけ書き換え**: `i-XXXXXXXXXXXXXXXXX` を手順書 01 Step 4 でメモした実際のインスタンス ID に置き換えてください。

```
Host dev-ec2
    HostName i-XXXXXXXXXXXXXXXXX
    User ubuntu
    Port 22
    IdentityFile ~/.ssh/dev-ec2-key.pem
    ProxyCommand C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe "aws ssm start-session --target %h --document-name AWS-StartSSHSession --parameters portNumber=%p"
```

3. 上書き保存（Ctrl+S）して閉じます

> 各行の意味: `Host` = この設定の呼び名 ／ `HostName` = 接続先（インスタンス ID）／ `User` = EC2 側のユーザー名（Ubuntu の AMI は `ubuntu` 固定）／ `IdentityFile` = Step 4 で置いた秘密鍵 ／ `ProxyCommand` = 「接続の通り道として、まず SSM のトンネルを開け」という肝の1行です。

> ⚠️ メモ帳の保存で `config.txt` になってしまうと動きません。保存後に PowerShell で `dir $env:USERPROFILE\.ssh` を実行し、ファイル名が拡張子なしの `config` であることを確認してください（`config.txt` になっていたら `Rename-Item "$env:USERPROFILE\.ssh\config.txt" "config"` で直せます）。

## Step 6: コマンドで接続テスト

### なぜやるか

VS Code は SSH の上に乗っているだけなので、先に土台の SSH 単体を確認します。ここが通れば、VS Code で問題が起きても「VS Code 側の問題」と絞り込めます（01 Step 5 と同じ考え方です）。

### 操作

EC2 が「実行中」であることを確認して（停止していれば AWS 画面で選択 → インスタンスの状態 → 開始）、PowerShell で:

```powershell
ssh dev-ec2
```

- 初回は `Are you sure you want to continue connecting (yes/no/[fingerprint])?` と聞かれます。これは「初対面の相手ですが信用しますか」という確認です。**`yes`** と入力して Enter
- `ubuntu@ip-10-0-…:~$` のような緑のプロンプトが出れば**成功**。あなたは今 EC2 の中にいます
- `exit` と入力して Enter で抜けます

### うまくいかないとき

| 症状 | 原因と対処 |
|---|---|
| `UNPROTECTED PRIVATE KEY FILE` | 鍵の権限が緩い。Step 4 の icacls 2行を再実行 |
| `TargetNotConnected` | EC2 が停止している（AWS 画面で開始する）／起動直後で SSM への名乗り出がまだ（5分待つ）／01 Step 4 の IAM ロール付け忘れ（01 Step 5 の対処参照） |
| `名前 dev-ec2 を解決できません` 系 | Step 5 の config が読まれていない。ファイル名（config.txt になっていないか）と置き場所を確認 |
| 反応がなく固まる | Step 3 の plugin 未インストール、または社内プロキシ。`session-manager-plugin` 単体実行と付録を確認 |

## Step 7: VS Code Remote-SSH で接続する

### 操作

1. VS Code を開き、左端のブロック4つのアイコン（**拡張機能**）をクリック → 検索窓に「**Remote - SSH**」→ Microsoft 製の「Remote - SSH」を「**インストール**」
2. キーボードで **F1** キーを押す（コマンド入力欄が開く）→「**Remote-SSH: ホストに接続...**」と入力して選択
3. 接続先の候補に **`dev-ec2`** が出るのでクリック（Step 5 の設定ファイルを VS Code が自動で読んでいます）
4. 新しいウィンドウが開き、初回のみ:
   - 「このホストのプラットフォームを選択」→ **Linux**
   - 1〜2分の初期セットアップが走ります（EC2 側に VS Code の本体処理部分＝ VS Code Server を自動インストールしている。2回目以降はすぐ繋がります）
5. 左下の緑（または青）のステータスに「**SSH: dev-ec2**」と表示されれば接続完了

### 確認

- メニュー「ターミナル」→「新しいターミナル」で `ubuntu@ip-…$` のプロンプトが出ること。**この VS Code のターミナルはもう EC2 の中**です。以降、手順書 03 の作業はこのターミナルで行います

## Step 8: 起動・停止スクリプトを作る

### なぜ必要か

毎朝 AWS の画面にログインして起動するのは面倒だからです。デスクトップに「ダブルクリックで EC2 を起動」「同じく停止」の2つのスクリプトを置きます（停止は毎晩自動ですが、早く切り上げる日に手で止めれば、その分課金も止まります)。

### 操作

1. メモ帳を開き（スタート →「メモ帳」）、以下を貼り付けます。**`i-XXXXXXXXXXXXXXXXX` を自分のインスタンス ID に書き換え**てください:

```bat
@echo off
aws ec2 start-instances --instance-ids i-XXXXXXXXXXXXXXXXX --region ap-northeast-1
echo.
echo Start signal sent. Wait 1-2 minutes, then connect from VS Code.
pause
```

2. 「ファイル」→「名前を付けて保存」→ 保存先: デスクトップ、ファイル名: **`"EC2起動.bat"`**（**ダブルクォーテーションごと**入力すると `.txt` が付かずに保存できます）、文字コード: **ANSI**
3. 同様にもう1つ、以下を **`"EC2停止.bat"`** として保存します:

```bat
@echo off
aws ec2 stop-instances --instance-ids i-XXXXXXXXXXXXXXXXX --region ap-northeast-1
echo.
echo Stop signal sent.
pause
```

> メッセージが英語なのは、bat ファイルの文字コード事情による文字化けを避けるためです（動作には関係ありません）。

### 確認

- `EC2停止.bat` をダブルクリック → 黒い画面に `"CurrentState": { … "Name": "stopping" }` を含む応答 → AWS 画面でインスタンスが「停止済み」になる
- `EC2起動.bat` をダブルクリック → 同様に `"pending"` → 1〜2分後に「実行中」→ VS Code から接続できる

これで毎日の流れは「**朝: EC2起動.bat → VS Code を開いて dev-ec2 に接続 → 作業 → 夜: 21:00 に勝手に停止**」になります。

## 付録: プロキシ設定（Step 2 の確認が失敗した場合のみ）

会社のネットワークが外部通信をプロキシ（関所）経由に限定している場合、AWS CLI に関所の場所を教える必要があります。

1. **プロキシのアドレスを調べる**: 社内の IT 部門に「社外への HTTPS 通信のプロキシサーバーのアドレスとポートを教えてください」と確認するのが確実です（ブラウザは通れているので、ブラウザには設定済みのはずです。Windows の「設定 → ネットワークとインターネット → プロキシ」で見えることもあります）
2. **環境変数に設定する**: PowerShell で以下を実行（アドレスとポートは調べた値に置き換え）:

```powershell
[System.Environment]::SetEnvironmentVariable("HTTPS_PROXY", "http://プロキシのアドレス:ポート", "User")
```

3. PowerShell を開き直して Step 2 の確認コマンドを再実行してください
4. それでも通らない場合は、プロキシが認証付き（ユーザー名・パスワード要求）の可能性があります。形式は `http://ユーザー名:パスワード@アドレス:ポート` ですが、ここまで来たら IT 部門との相談を推奨します
