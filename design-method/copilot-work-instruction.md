# 作業指示書: 設計書マークダウン化 + トレーサビリティ導入

設計書をMarkdown化し、要件・設計・実装をリンクで辿れる状態（Requirements Traceability）を
作るための作業指示書。VS Code + GitHub Copilot 環境で参照する。

## 背景

- DWS案件（COBOL→Java移行、417機能 + バッチ37本）は設計書をExcelからMarkdownへ移行する。フォーマット変更の許可は取得済み
- 現行のExcel→md自動変換は不要行を含み、無駄トークンが発生している。Copilotに1タスクで必要な設計情報だけを読ませる形が必要
- 設計書は序盤はExcel入力（別チーム作成）、後半はMarkdown直書きに切り替わる二本立て期間が発生する
- 既存の共通対応マップ（`pattern-catalog/templates/traceability-map.md`）はシート↔実装ファイル対応を持つが、確信度「低」・有識者確認「未」の状態
- CIは現在使用不可（将来解禁の可能性あり）

## 目的

- 任意のJavaファイルを起点に、関連する設計書md・DBテーブル・業務ルールをgrepで辿れる状態にする
- 設計書変更時の影響範囲（修正対象ファイル一覧）を機能IDのgrepで機械的に特定できる状態にする
- Copilotが1生成タスクで読む設計書を、必要なmdファイル2〜4個に限定できる状態にする

## やること（成果物と制約）

### 1. mdフォーマット定義（テンプレート + 記入例）

設計書Markdownの唯一の「正」となるフォーマット定義。

- **Excel変換ツールと直書きテンプレートの両方がこの定義に従う**こと。変換ルールが正ではなく、フォーマット定義が正。変換出力と直書きが構造・セクション見出しレベルで区別不能であること
- 確信度「高」まで検証済みのシート↔ファイル対応マップに基づくこと（現状の「低・未確認」のまま確定させない）
- 各mdファイル種別に必須セクションを定義すること（後述のフォーマット準拠lintの判定基準になる）

### 2. spec/ ディレクトリ構造

分割の原則: **消費者（生成するJavaファイル種別）ごとに切る**。章立てやExcelシート構成の踏襲ではない。

```
spec/
├── front/FUNC-xxxx/
│   ├── layout.md       ← 画面レイアウト
│   ├── items.md        ← 項目定義
│   └── validation.md   ← バリデーション
├── back/FUNC-xxxx/
│   ├── methods.md      ← 画面で使うメソッド
│   └── logic.md        ← 業務ロジック
├── db/
│   └── <テーブル物理名>.md   ← テーブル単位（機能単位ではない）
├── rules/
│   └── BR-xxxx.md      ← 業務ルール（ID台帳）
└── common/
    └── *.md            ← 全画面共通部（各機能ディレクトリに複製しない）
```

制約:

- 機能ID（既存の管理番号）をディレクトリ名・ファイル名のキーにする。**リネーム禁止**。タイトル変更はファイル内のh1で吸収する
- 業務ルールはパスではなくID（BR-xxxx）で参照する。1ルールが複数機能にまたがるため
- 分割粒度: **1生成タスクが読むmdは2〜4ファイル**に収まること。消費者が同じシート同士は分割しない（分割理由が「消費者が違う」以外なら統合する）
- バッチ37本は画面と別の消費マトリクスを持つこと。画面用分割（layout/items/validation）を流用しない

### 3. 消費マトリクス（全機能共通ルール）

Javaファイル種別ごとに「読む設計書md」を定義した表。全417機能で共通の1枚。

| 生成するファイル | 読む設計書（初期案・要検証） |
|---|---|
| Form | items.md + validation.md |
| DTO | items.md |
| Thymeleafテンプレート | layout.md + items.md（+ common/） |
| Controller | methods.md + validation.md |
| Service | methods.md + logic.md + 該当テーブルのdb/*.md |
| Repository / Entity | 該当テーブルのdb/*.md |

- 上記は確信度「低」の初期案。確定は検証済み対応マップに基づくこと
- この表から各Javaファイルのリンクヘッダが機械的に導出できること（機能IDとテーブル名の差し込みのみで決まる状態）

### 4. リンクヘッダ規約

Javaファイル先頭のJavadocカスタムタグでコード→設計書リンクを表現する。

```java
/**
 * @spec-front spec/front/FUNC-0123/items.md
 * @spec-back  spec/back/FUNC-0123/methods.md
 * @spec-db    spec/db/T_ORDER.md
 * @biz-rule   BR-0045
 */
```

制約:

- 疑似XMLタグではなくJavadocカスタムタグ（`@spec-front` / `@spec-back` / `@spec-db` / `@biz-rule`）を使う
- **ワイルドカード禁止**・1行1リンク
- ヘッダは消費マトリクスから導出する（人が機能ごとに考えて書くものにしない）。コード生成時にヘッダも同時に生成されること
- パターンレシピの生成手順にヘッダ付与を含めること

### 5. 検証スクリプト

以下4機能を持つスクリプト1本（Python想定）。

| 機能 | 内容 |
|---|---|
| リンク実在チェック | ヘッダが参照するmd・BR-IDが実在するか |
| ヘッダ網羅チェック | 対象のJavaファイル種別すべてにヘッダがあるか |
| フォーマット準拠lint | 各mdがフォーマット定義の必須セクションを満たすか |
| 逆引きマップ生成 | ヘッダを集約し traceability-map（設計書→実装ファイル）を自動生成する |

制約:

- 逆引きマップは**手動維持しない**。常にスクリプト生成物とする
- CIなしで完結すること: ローカル実行のみで全機能が動作し、ワークフローの完了条件（tasks.mdのチェック項目等）として組み込める形にする。将来CIが解禁されたら無変更で載せ替え可能であること

### 6. Excel変換ルール表

別チーム作成のExcelを受け入れるための「Excelシート→mdセクション」対応表（機能横断で1枚）。

- 別チームのExcelフォーマット変更時に、この表の修正だけで追従できる構造にすること
- 変換ツール本体はこの表とmdフォーマット定義に従うこと

## 完了条件（機械判定）

- [ ] 検証スクリプトが代表機能に対して4機能すべて正常終了する（exit 0）
- [ ] 代表機能1機能ぶんのspec/配下mdがフォーマット準拠lintを通過する
- [ ] 代表機能の生成Javaファイル全種別にリンクヘッダが存在し、リンク実在チェックを通過する
- [ ] 逆引きマップがスクリプトで再生成でき、手動編集なしで代表機能の対応を網羅している
- [ ] Copilotに「FUNC-xxxx に関連する設計書・テーブル・業務ルールをすべて挙げて」と質問し、ヘッダとspec/構造だけを根拠に正答する
- [ ] 消費マトリクスの各行の確信度が「高」（DCS複数機能で確認済み）である
- [ ] Excel変換出力と直書きテンプレートが同一機能で構造diffゼロになる

## スコープ外

- 417機能全量のExcel→md変換の実施（本指示書はフォーマットと仕組みの確立まで）
- DB設計書の中身の作成（別チーム所管。受け入れフォーマットの定義のみ本作業の範囲）
- CI環境の構築
- メソッド単位・行単位の細粒度トレーサビリティ（ファイル単位で止める）
- 要件（req）→設計のリンク整備（機能IDを通す方針のみ維持し、本指示書の対象は設計↔実装）
