T-* Markdownテンプレート

spec 生成用の Markdown テンプレート12本（T-items〜T-warnings）が、どの spec ファイルを・どんな節構成で・どの生成条件のときに作るかを一覧します。振り分け規則の正本は spec-format/routing-table.md で複製しません。

/02-run /01-setup verify.ps1 /03-check

大半のテンプレートは /02-run が spec・trace 生成タスクで使います。T-warnings のみ4工程すべてが書き込みます（各カード下部の「書く/読む」参照）。

T-items contracts/markdown/T-items.template.md

作る spec ファイル: spec/front/{画面ID}/items.md

生成条件（output-structure.md §2）: 画面項目レコードがある

節構成: 1. 画面項目（screen_item） 2. 表示モード（display_mode） 3. URL・パラメータ（parameter_definition） 4. 共通仕様参照

書く: /02-run（spec生成タスク） 読む: verify.ps1、/03-check

T-layout contracts/markdown/T-layout.template.md

作る spec ファイル: spec/front/{画面ID}/layout.md

生成条件（output-structure.md §2）: layout_reference レコードがある

節構成: 1. レイアウト・表示モード 2. レイアウト明記事項・Thymeleaf仕様 3. アセット参照

補足: AI がレイアウトを推測して補完しない（設計書に明記された内容のみ）。

書く: /02-run（spec生成タスク） 読む: verify.ps1、/03-check

T-validation contracts/markdown/T-validation.template.md

作る spec ファイル: spec/front/{画面ID}/validation.md

生成条件（output-structure.md §2）: バリデーション系レコードがある

節構成: 1. バリデーション（validation_rule） 2. 項目制御（item_control） 3. 相関バリデーション（correlation_validation） 4. メッセージ（message_rule） 5. 共通仕様参照

補足: 条件・否定・例外・数値・順序を JSON から欠落させない（意味照合 /03-check の対象）。

書く: /02-run（spec生成タスク） 読む: verify.ps1、/03-check

T-methods contracts/markdown/T-methods.template.md

作る spec ファイル: spec/back/{機能ID}/methods.md

生成条件（output-structure.md §2）: ui_event / process_section 概要 / 画面文脈 external_interface がある

節構成: 1. イベント・遷移（ui_event） 2. 処理概要（process_section／概要） 3. 外部連携（external_interface／画面文脈） 4. 業務ロジック本文参照（logic.md へリンクのみ）

書く: /02-run（spec生成タスク） 読む: verify.ps1、/03-check

T-logic contracts/markdown/T-logic.template.md

作る spec ファイル: spec/back/{機能ID}/logic.md（バッチは batch/{ジョブID}/logic.md に本テンプレートを流用。id はジョブIDにする）

生成条件（output-structure.md §2）: process_section 本文がある（バッチはバッチのロジックがある）

節構成: 1. 業務ロジック（process_section） 2. 詳細ロジック記述 3. 業務ルール参照（spec/rules/BR-{番号}.md へリンクのみ）

補足: 条件・否定・例外・数値・順序を JSON から一切欠落させない（意味照合 /03-check の第一対象）。

書く: /02-run（spec生成タスク） 読む: verify.ps1、/03-check

T-queries contracts/markdown/T-queries.template.md

作る spec ファイル: spec/back/{機能ID}/queries.md（バッチは batch/{ジョブID}/queries.md に本テンプレートを流用。id はジョブIDにする）

生成条件（output-structure.md §2）: search/update/select_constraint/item_db_mapping がある（バッチはバッチの検索/更新要領がある）

節構成: 1. 検索要領（search_requirement） 2. 更新要領（update_requirement） 3. 抽出制約（select_constraint） 4. 画面項目・DB項目対応（item_db_mapping） 5. テーブル定義参照（db/ へリンクのみ）

補足: JSON に無い SQL・条件を創作しない。テーブルの物理定義は複製せず db/{テーブル物理名}.md へリンクする。

書く: /02-run（spec生成タスク） 読む: verify.ps1、/03-check

T-db-table contracts/markdown/T-db-table.template.md

作る spec ファイル: spec/db/{テーブル物理名}.md（ファイル名はテーブル物理名・ASCII）

生成条件（output-structure.md §2）: テーブル/VIEW 定義レコードがある

節構成: 1. テーブル概要（attribute_definition） 2. カラム定義（entity_field） 3. VIEW定義（view_definition） 4. VIEW検索ブロック（view_query_block） 5. 関連参照（_er-overview.md へリンクのみ）

補足: db/ は共有領域。既存記述と矛盾する定義（型・桁の不一致）を検出したら上書きせず両論併記し warnings.md に記録する。JSON に無い型・桁は推測で埋めない（未確認は null、該当なしは空）。

書く: /02-run（spec生成タスク） 読む: verify.ps1、/03-check

T-er-overview contracts/markdown/T-er-overview.template.md

作る spec ファイル: spec/db/_er-overview.md

生成条件（output-structure.md §2）: 全体テーブル定義書が取り込まれている場合のみ（機能単位のエンティティ定義書だけの段階では作らない）

節構成: 1. テーブル一覧 2. ER図（mermaid erDiagram） 3. 関連一覧（entity_relation）

補足: 関連線として描いてよいのは explicit（設計書に明記された関連）と derived_join（VIEW定義・検索要領のJOIN条件由来）の2種のみ。AI の推測による関連生成は禁止（J-30 entity_relation）。

書く: /02-run（spec生成タスク） 読む: verify.ps1、/03-check

暫定: バッチの標準ファイルセット（control.md / io.md / logic.md / queries.md）は実物のバッチ設計書での検証後に確定する（output-structure.md §3）。

T-trace contracts/markdown/T-trace.template.md

作る spec ファイル: spec/trace/{機能ID}.md（モデルは GPT-5.4 固定。他テンプレートは GPT-5.4 | GPT-5.4 mini）

生成条件（output-structure.md §2）: 対象機能の spec ファイルが生成済み

節構成: 1. クラス図（mermaid classDiagram） 2. 設計→実装対応表 3. ER断片（_er-overview.md の有無で分岐） 4. 消費マトリクス抜粋

補足: クラス名の命名規則・配置パス規則の正本は spec/common/src-mapping.md（本テンプレートは参照のみ）。消費マトリクスの正本は spec-format/consumption-matrix.md（暫定・ここは抜粋のみ）。

書く: /02-run（trace生成タスク） 読む: verify.ps1（トレース照合）

T-warnings contracts/markdown/T-warnings.template.md

作る spec ファイル: runs/{ID}/20-check/warnings.md（追記型の台帳。ラン開始時に常設）

生成条件（output-structure.md §2）: ラン開始時に常設

節構成: 種別（機械FAIL / 機械WARN / EV指摘 / 未レビュー / 矛盾検出） × 内容 × 発生工程 × 状態（未解消 / 解消）の1枚表

種別の意味: 機械FAIL=JSON破損・sourceRefs欠落・routingPlanに無いシート等（停止条件。verify.ps1 も出力） / 機械WARN=verify.ps1 の非ブロッキング警告（ルーティング未生成・リンク切れ・lint指摘等） / EV指摘=/03-check（意味照合）の findings / 未レビュー=人間レビュー未実施のまま進行中（非ブロッキング） / 矛盾検出=共有領域（db/ common/ rules/）で既存記述と矛盾する定義を検出（両論併記のうえ人間判断待ち）

運用: /01-setup /02-run /03-check・verify.ps1 が検出のたびに1行追記し、解消したら状態を「解消」に更新する。

書く: /01-setup（未レビュー・未知フォーマット） 書く: /02-run（機械FAIL・矛盾検出） 書く: verify.ps1（機械FAIL・機械WARN・矛盾検出） 書く: /03-check（EV指摘） 読む: /02-run（冒頭確認・毎回要約表示）、人間

バッチの流用テンプレートについて

バッチの業務ロジック（batch/{ジョブID}/logic.md）と検索/更新（batch/{ジョブID}/queries.md）には専用テンプレートが無く、画面/機能用の T-logic / T-queries をそのまま流用する（id はジョブIDにする）。専用テンプレートを持つのは制御（T-batch-control）と入出力（T-batch-io）の2つのみ。
