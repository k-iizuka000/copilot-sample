作業フォルダ雛形（runs/{機能ID}）

run-template/FEATURE-ID/ は1機能ぶんの作業を進めるフォルダの雛形。コピーして機能IDに名前を変え、run-request.json を記入してから /01-setup を実行する。

/01-setup が読む /02-run が読み書きする verify.ps1 が読み書きする /03-check が読み書きする 人間が用意・確認する

フォルダツリー

見方: run-template/FEATURE-ID/ をコピーし、フォルダ名を機能IDに変えて runs/ 配下に置く（例: runs/FUNC0123/。RUNBOOK 初回セットアップ手順2より）。

runs/{機能ID}/
├── run-request.json   機能ID・機能名・設計書・出力先を記入する定義ファイル（人間が記入）
├── 00-input/           設計書スナップショット（CSV/TSV 等）を置く
├── 10-json/            出典付きの中間 JSON（J-*）。自動生成
└── 20-check/           verify結果・warnings・check結果。自動生成
output-structure.md §1 では 00-input/ に画像等のアセット置き場 assets/ も含められるとされている。

run-request.json の全キー

書く: 人間（作業フォルダ準備） 読む: /01-setup

見方: RUNBOOK 初回セットアップ手順3「機能ID・機能名・設計書ファイル名・出力先（spec/）を記入して保存する」に沿って、表の上から埋めていく。

キー役割雛形の値
featureId機能ID（RUNBOOKより）FEATURE-ID
featureName機能名（RUNBOOKより）顧客マスタ照会
idTypeID種別の宣言。ID種別が判別できない場合はこの宣言を正とする（output-structure.md §4より）機能ID
designDocuments対象設計書の配列（下記4キーを要素に持つ）—
　├ documentType設計書の種別screen_design
　├ profileId適用する設計書プロファイルのIDPROFILE-01
　├ sourcePath設計書ファイル名。00-input/ 配下に置いたファイルを指す（00-input/README.mdより）00-input/screen-design.csv
　└ version設計書のバージョン1.0
outputSpecRoot出力先。spec/ を記入する（RUNBOOKより）spec
operator作業者を表すフィールドyamada.taro

00-input/

設計書のスナップショット（CSV/TSV 等）を置く（README.mdより）。Excel を直接読めない場合は対象シートを CSV/TSV に書き出してここへ置く。この書き出しは人間が行う前処理で、Prompt の工程ではない。

書く: 人間（前処理） 読む: /01-setup 読む: /02-run（抽出）

10-json/

/01-setup と /02-run が出力する、出典付きの中間 JSON（J-* ファイル）が入る（README.mdより）。人間が手で書き換える必要はない。

書く: /01-setup（J-01） 書く/読む: /02-run（抽出・生成タスク） 読む: verify.ps1 読む: /03-check

20-check/

自動チェックの結果が入る（README.mdより）: verify.ps1 の結果（verify-result.md）、警告一覧（warnings.md）、/03-check の意味照合結果（check-result.md）など。困ったときはまず warnings.md を読む。

書く: /01-setup（未レビュー・未知フォーマット→warnings.md） 書く: /02-run（機械FAIL・矛盾検出→warnings.md） 書く: verify.ps1（verify-result.md・reverse-map.md・warnings.md） 書く: /03-check（check-result.md、EV指摘→warnings.md） 読む: 人間
v2.1.0 にあった承認ファイル（status.md 等）はここには無い。承認ファイル（G0/G1/G2 のようなゲート）は使わず、人間確認の状態を JSON や Markdown に持たせない（原本: copilot-instructions.md「ゲートと停止条件」より）。
