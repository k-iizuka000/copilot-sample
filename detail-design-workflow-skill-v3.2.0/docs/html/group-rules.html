共通ルール（実行ルールの正本）

.github/copilot-instructions.md の全9節。/01-setup・/02-run・/03-check の全 Prompt File はこのルールに従い、同じ制約をそれぞれの Prompt File 側には複製しない。

このファイルは 全 Prompt 共通の暗黙コンテキストです。/01-setup・/02-run・/03-check のいずれも実行時にこのルールを読み込んでおり、各工程ページの「入力」欄にも参照として現れます。
/01-setup /02-run /03-check が共通ルールとして読む

対象範囲（スコープ）

  • 目的: Excel設計書を出典付き JSON（J-* JSON）へ変換し、その JSON から責務分割された詳細設計 Markdown（spec/ ツリー）を作る。
  • スコープ外: コード実装・実装計画・テストコードの作成/変更はしない。設計と実装の対応（クラス名・パス規則）は spec/trace/ と spec/common/src-mapping.md に「予定」として記すだけで、実コードは生成しない。
  • 元の設計書は変更しない。Prompt File が指定した出力先以外を変更しない。

根拠と出典

  • 業務仕様の根拠は、run-request.json の designDocuments に登録された Excel設計書（00-input/ に置かれた原本コピー）だけにする。
  • 指定されていない設計書・既存コード・Web・別ブックを根拠に使わない（原本外根拠の禁止）。
  • 確定した各レコードには1件以上の sourceRefs を必ず付ける。出典の無い仕様は書かない。
  • sourceRef は { workbook, sheet, range, displayedValue, formula(取得できれば), evidenceType } とする。
  • 設計書に書かれていない内容を AI が推測で補わない。読み取れない・判断できないものは推測せず「未確認」として残す。

「該当なし」と「未確認」の区別（混同禁止）

[]（空配列）＝該当なし資料を確認した結果、対象レコードが無い状態。
null＝未確認資料不足・読み取り不能・判断不能で確定できない状態。

この2つを混同しない。空文字や「不明」などの文字列で代用しない。

JSON出力（J-* JSON）

  • contracts/json/ の対応スキーマに従う。定義外のキーは増やさない。軽量モデルがスキーマから外れても全停止はさせない — 構造の最終チェックは verify.ps1 が行う。
  • 各レコードは recordId（一意）／recordType／layers／scope／sourceRefs（1件以上）／evidenceState を持つ。
  • recordId 形式: {機能ID or 画面ID}-{recordTypeの略号}-{連番3桁}（例: FUNC0123-ITEM-012）。
  • evidenceState: explicit（原本に明記）／derived（原本の記述から導出）／ambiguous（判断保留）。
  • 同じ入力に対しては ID と並び順を安定させる。
  • 数式を取得できる場合は表示値と数式文字列の両方を保持する。
  • 非表示行・列を、非表示であることだけを理由に除外しない。
  • 画像・図形・コメント等は見た目から仕様を推測せず、アセットとして分離し layout.md からリンクする。
  • レコードの網羅性（数え上げ）をモデルの自己申告で保証しない。網羅性の照合は verify.ps1（機械照合）と人間レビューで行う。

ER関連（entity_relation）の生成規則

  • テーブル間の関連（entity_relation レコード）は、設計書に明記された関連だけを作る。
    • basis=explicit: 設計書のテーブル定義・関連欄に明記された関連。
    • basis=derived_join: VIEW 定義・検索要領の JOIN 条件から導出した関連（導出元を sourceRefs に残す）。
  • AI の推測による関連線（設計書に根拠が無い FK・参照の想像）は禁止。
  • ER図（Mermaid）は、全体テーブル定義書がある場合にだけ作る。機能単位のエンティティ定義しか無い段階では ER図を作らず、テーブル定義の取り込みのみ行う。

出力起点ルーティングの原則

  • レコードの出力先は「どの設計書から来たか」ではなく「レコードの責務」で決める。実際の対応表は spec-format/routing-table.md を正とする。
  • 1冊の設計書が複数の spec ファイルに分かれるのは正常。1つの spec ファイルに複数の設計書由来のレコードが集まるのも正常。
  • 共有領域（spec/db/・spec/common/・spec/rules/）は、該当レコードを持つどの作業でも追記・更新してよい。既存の記述と矛盾する内容を検出したら、上書きせず両論併記とし、warnings.md へ警告を残して人間の判断に委ねる。

Markdown出力（spec/ ツリー）

  • contracts/markdown/ のテンプレートに従う。
  • 各仕様行には Record ID と出典（シート名!範囲 の短縮表記）を付ける。JSON に無い仕様を Markdown 側で創作しない。
  • 対応する確定レコードが無い分野のファイルは作らない。共通仕様は各ファイルへ全文複製せず、spec/rules/ または spec/common/ へのリンクで参照する。

ゲートと停止条件

停止するのは機械FAILのときだけ（JSON が壊れている・sourceRefs 欠落・ルーティング表に無い種別/シート 等）。検出したらそのタスクを実行せず warnings.md に記録して止まる。
人間レビューは非ブロッキング。未レビューでも作業は止めない。未解消の警告は warnings.md に一覧として残し、実行のたびに要約表示する。

承認ファイル（status.md や G0/G1/G2 のようなゲート）は使わない。人間確認の状態を JSON や Markdown に持たせない。

参考（RUNBOOKより）: /03-check の意味照合の判定は PASS / PASS_WITH_WARNINGS / FAIL の3値。これも人間レビューと同じく非ブロッキングで、FAIL でも成果物は自動修正されない（直すときは /02-run を再実行）。詳しくは prompt-03-check.html。

チャット応答

  • 指定された成果物だけを作成・更新する。
  • 最終応答は、やったこと・出力先・作成/省略/削除したファイル・件数・判定・未解消の警告だけを簡潔に報告する。
