**日付**: 2026-07-15

**位置づけ**: 本書は v3.2.0 の変更の What（何が出来ていればよいか）の正本。日々の操作手順は RUNBOOK.md、実行ルールは copilot-instructions.md を参照。

## 背景

v3.1.0 までは、変換の前に人間が①作業フォルダの雛形コピー ②run-request.json の手書き ③Excel の CSV/TSV 書き出し、という3つの前処理を行う設計だった。実際の現場（DWS案件・仕事PC）では Copilot が生の .xlsx を読み取れることが確認されており、この前処理はユーザーの完成イメージ（「Excel と出力先を渡すだけで全部できる」）と食い違っていた。設計書フォーマット自体は修正可能で、要望書（design-doc-request.md）に合わせた修正が予定されている。

## 目的（完成形）

**ユーザーが渡すのは「インプットの Excel（生の .xlsx）」と「出力パス」の2つだけ。** あとは案内に従ってプロンプトを実行し続ければ、詳細設計 Markdown（spec/ ツリー）が漏れなく完成する。

```text
ユーザーの作業 = Excel を用意 → /01-setup（Excelパス・出力先を伝える）
              → /02-run を案内が終わるまで繰り返す
              → verify.ps1 を実行 → /03-check（別チャット）
```

## 決定事項

1. **入力は生の .xlsx**。人間による CSV/TSV への書き出しは廃止する。Copilot が直接読み取る（必要なら Agent の使える手段＝ターミナルコマンド等を用いてよい）。
2. **読み取り失敗時は原因を報告して停止**する（破損・保護ビュー・パスワード付き等）。CSV/TSV の提出は求めない。推測で続行しない。
3. **run-request.json は /01-setup が自動生成**する。作業フォルダ（runs/{ID}/）の作成、Excel 原本の 00-input/ へのコピーも自動。人間の手書き・手動コピーは廃止する。
4. **命名規約**: `{設計書種別}_{ID}_{機能名}.xlsx`（正本: [design-doc-request.md](./design-doc-request.md) の第2項）。
   - ID 体系: 英字2字+数字2桁（例 `ab12`）= 機能ID（バッチ系）／英字2字+数字4桁（例 `ab1234`）= 画面ID（機能ID+枝番2桁）。**桁数で機械判定できる**。
   - 設計書種別の語彙は暫定（画面設計書／機能設計書／DB設計書）。正式名称の確定後に要望書側を更新する。
5. **空欄の扱い**: ファイル名から取得できなかった項目は run-request.json に空欄のまま生成し、追加のファイルは作らない。
   - featureId（ID）の空欄のみ停止条件（「空欄を埋めて /01-setup を再実行して」と案内）。ID は作業フォルダ名・出力ファイル名に使うため。
   - それ以外の空欄は項目名をチャットで伝えたうえで続行する（人間が後から埋める）。
6. **入力の単位はまず1冊ずつ**。同じ機能の2冊目・3冊目は /01-setup の再実行で designDocuments に追記する。精度が安定したら機能単位（フォルダ）でのまとめ投げに拡張する（将来。本バージョンのスコープ外）。
7. **要望書準拠のフォーマット修正で精度を上げる**: A1 役割タグ・行ID・関連欄・結合セル回避に加え、命名規約（第2項）を要望書に明記し、プロンプトから要望書へリンクする。
8. **パッケージは v3.2.0 の新フォルダ**として作る（v3.1.0 は変更しない。フォルダ並置の流儀を踏襲）。
9. 教材（入力→出力ペア）を残す仕組みの追加は**行わない**（オーナー判断 2026-07-15）。
