runフォルダ雛形

原本: run-template/FEATURE-ID/ 一式
このページの目的と見方: 1 run（原則1画面または1機能）につきrun-template/FEATURE-IDをコピーして使う雛形フォルダの構成を見る。まず全体の配置（フォルダ構成）を見てから、入力確定ファイル（run-request.json）と人間確認状態の正本（status.md）を確認する。

どこから参照されるか:

/09 が status.md を statusPath として読む RUNBOOK G0/G1/G2 がこのフォルダの状態を記録 RUNBOOK「0. 入力を確定する」でコピーする

フォルダ構成

見方: 上のフォルダをコピーしたものが1 run。↓の6項目は同じ階層に並ぶファイル・フォルダで、実行順序ではない（RUNBOOK・各README.mdより）。

FEATURE-ID/機能IDに合わせて名前を変更してコピーする雛形フォルダ
↓
run-request.json入力確定情報の記入先
status.mdG0/G1/G2 人間確認状態の正本
00-input/設計書または入力スナップショットを格納する
10-json/J-* JSONを格納する
20-evaluation/EV-01とEV-02の評価結果を格納する
30-markdown/M-* 詳細設計Markdownを格納する

各フォルダの役割1行は、それぞれのREADME.mdの記載そのまま。

run-request.json

run開始時にrun-template/FEATURE-IDをコピーし、機能IDに合わせて名前を変更したうえで記入する入力確定ファイル（RUNBOOK「0. 入力を確定する」より）。

フィールド内容
contractId雛形では固定値 I-00
featureId機能ID（記入項目）
featureName機能名（記入項目。雛形ではnull）
runId実行ID（雛形例: FEATURE-ID-RUN-001）
designDocuments[].documentType雛形例: screen_design
designDocuments[].profileId雛形例: PROFILE-01
designDocuments[].sourcePath設計書パス（記入項目）
designDocuments[].version版（記入項目。雛形ではnull）
outputRoot出力先（記入項目。雛形例: work/detail-design/FEATURE-ID/RUN-001）
operator実行者（雛形ではnull）
humanGate.G0G0の状態（雛形ではnot_approved）
G0として人間が確認する項目（RUNBOOKより）
  • 対象設計書の正本と版
  • 機能IDと機能名
  • 使用するプロファイル
  • JSON、評価、Markdownの出力先
確認できない場合は開始しない。G0/G1/G2の全体像は group-skill-runbook.html#gates →。

status.md

G0/G1/G2の人間確認状態を記録する表。RUNBOOKは「J-90のhumanReviewStatusは評価時点のスナップショットであり、人間確認状態の正本はstatus.mdとする」と明記する。/09はstatusPathパラメータでこの表のG1状態を読み、「承認済み」でなければ停止する。
ゲート状態確認者日付備考
G0 入力確定未承認
G1 JSON承認未承認
G2 詳細設計承認未承認

状態は「未承認」または「承認済み」を使用する（雛形の注記より）。G1で「PASS_WITH_WARNINGS」を受容する場合は、備考へ対象J-90と受容理由を記録する。
