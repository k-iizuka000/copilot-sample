# /learn-eval - 抽出、評価、保存

スキルファイルを書き込む前に、`/learn` に品質ゲート、保存先の判断、知識の配置先への意識を追加します。

## 抽出する内容

以下を探します:

1. **エラー解決パターン** — 根本原因 + 修正 + 再利用性
2. **デバッグ技術** — 自明ではない手順、ツールの組み合わせ
3. **回避策** — ライブラリの癖、API の制限、バージョン固有の修正
4. **プロジェクト固有のパターン** — 規約、アーキテクチャ決定、統合パターン

## プロセス

1. セッションをレビューし、抽出可能なパターンを探す
2. 最も価値があり、再利用可能な洞察を特定する

3. **保存先を決定する:**
   - 問う: 「このパターンは別のプロジェクトでも役立つか？」
   - **Global** (`~/.claude/skills/learned/`): 2 つ以上のプロジェクトで使える汎用パターン（bash 互換性、LLM API の挙動、デバッグ技術など）
   - **Project**（現在のプロジェクト内の `.claude/skills/learned/`）: プロジェクト固有の知識（特定設定ファイルの癖、プロジェクト固有のアーキテクチャ決定など）
   - 迷った場合は Global を選ぶ（Global → Project への移動は、その逆より簡単）

4. 次の形式でスキルファイルを下書きする:

```markdown
---
name: pattern-name
description: "130文字未満"
user-invocable: false
origin: auto-extracted
---

# [説明的なパターン名]

**抽出日:** [日付]
**コンテキスト:** [いつ適用するかの簡単な説明]

## 問題
[これが解決する問題 - 具体的に]

## 解決策
[パターン/技術/回避策 - コード例付き]

## 使用タイミング
[トリガー条件]
```

5. **品質ゲート — チェックリスト + 総合判定**

   ### 5a. 必須チェックリスト（実際にファイルを読んで確認）

   下書きを評価する前に、以下を**すべて**実行します:

   - [ ] `~/.claude/skills/` と関連するプロジェクトの `.claude/skills/` ファイルをキーワードで grep し、内容の重複を確認する
   - [ ] MEMORY.md（プロジェクトとグローバルの両方）に重複がないか確認する
   - [ ] 既存スキルへの追記で十分かどうか検討する
   - [ ] 一度限りの修正ではなく、再利用可能なパターンであることを確認する

   ### 5b. 総合判定

   チェックリスト結果と下書きの品質を総合し、次のいずれか**1つ**を選びます:

   | 判定 | 意味 | 次のアクション |
   |---------|---------|-------------|
   | **Save** | 独自性があり、具体的で、適切なスコープ | ステップ 6 に進む |
   | **Improve then Save** | 価値はあるが改善が必要 | 改善点を列挙 → 修正 → 再評価（1回） |
   | **Absorb into [X]** | 既存スキルに追記すべき | 対象スキルと追記内容を提示 → ステップ 6 |
   | **Drop** | 些細、冗長、または抽象的すぎる | 理由を説明して終了 |

   **判断の観点**（判定の参考にするが、点数化はしない）:

   - **具体性と実行可能性**: すぐに使えるコード例やコマンドが含まれている
   - **スコープ適合性**: 名前、トリガー条件、内容が揃っており、1つのパターンに集中している
   - **独自性**: 既存スキルではカバーされていない価値がある（チェックリスト結果に基づく）
   - **再利用性**: 将来のセッションで現実的に発火するシナリオがある

6. **判定ごとの確認フロー**

   - **Improve then Save**: 必要な改善点 + 修正版の下書き + 1回の再評価後の更新済みチェックリスト/判定を提示する。修正版の判定が **Save** なら、ユーザー確認後に保存する。それ以外は新しい判定に従う
   - **Save**: 保存先パス + チェックリスト結果 + 1行の判定理由 + 下書き全文を提示する → ユーザー確認後に保存
   - **Absorb into [X]**: 対象パス + 追記内容（diff形式）+ チェックリスト結果 + 判定理由を提示する → ユーザー確認後に追記
   - **Drop**: チェックリスト結果と理由のみを示す（確認不要）

7. 決定した場所に保存または吸収する

## ステップ 5 の出力形式

```
### チェックリスト
- [x] skills/ grep: 重複なし（または: 重複あり → 詳細）
- [x] MEMORY.md: 重複なし（または: 重複あり → 詳細）
- [x] 既存スキルへの追記: 新規ファイルが適切（または: [X] に追記すべき）
- [x] 再利用性: 確認済み（または: 一度限り → Drop）

### 判定: Save / Improve then Save / Absorb into [X] / Drop

**理由:** （判定を説明する1-2文）
```

## 設計意図

この版では、以前の 5 次元の数値スコアリングルーブリック（Specificity、Actionability、Scope Fit、Non-redundancy、Coverage を 1-5 で採点）を、チェックリストベースの総合判定システムに置き換えています。現代の frontier model（Opus 4.6+）は強い文脈判断力を持っており、豊かな定性的シグナルを数値スコアに押し込むとニュアンスが失われ、誤解を招く合計点が生まれます。総合的なアプローチにより、モデルはすべての要素を自然に重み付けでき、明示的なチェックリストによって重要な確認漏れを防ぎながら、より正確な保存/破棄の判断を行えます。

## 注意事項

- 些細な修正（タイプミス、単純な構文エラー）は抽出しない
- 一度限りの問題（特定 API の障害など）は抽出しない
- 将来のセッションで時間を節約できるパターンに焦点を当てる
- スキルは集中させる — 1つのスキルに1つのパターン
- 判定が Absorb の場合は、新しいファイルを作成せず既存スキルに追記する
