# チームビルダー

必要に応じてエージェントチームを閲覧・構成するためのインタラクティブメニュー。フラットなエージェントコレクションと、ドメイン別サブディレクトリのコレクションの両方で動作します。

## 使用するタイミング

- 複数のエージェントペルソナ（Markdownファイル）があり、タスクに使用するものを選びたい
- 異なるドメイン（例：Security + SEO + Architecture）からアドホックなチームを構成したい
- 決める前に利用可能なエージェントを閲覧したい

## 前提条件

エージェントファイルは、ペルソナプロンプト（アイデンティティ、ルール、ワークフロー、成果物）を含むMarkdownファイルである必要があります。最初の `# 見出し` がエージェント名として、最初の段落が説明として使用されます。

フラットレイアウトとサブディレクトリレイアウトの両方をサポートします。

**サブディレクトリレイアウト** — ドメインはフォルダ名から推定されます。

```
agents/
├── engineering/
│   ├── security-engineer.md
│   └── software-architect.md
├── marketing/
│   └── seo-specialist.md
└── sales/
    └── discovery-coach.md
```

**フラットレイアウト** — ドメインは共有されたファイル名プレフィックスから推定されます。2つ以上のファイルが共有するプレフィックスはドメインとして扱われます。一意のプレフィックスを持つファイルは「General」に入ります。注意：アルゴリズムは最初の `-` で分割するため、複数語のドメイン（例：`product-management`）では代わりにサブディレクトリレイアウトを使用してください。

```
agents/
├── engineering-security-engineer.md
├── engineering-software-architect.md
├── marketing-seo-specialist.md
├── marketing-content-strategist.md
├── sales-discovery-coach.md
└── sales-outbound-strategist.md
```

## 設定

エージェントディレクトリは順番に探索され、結果はマージされます。

1. `./agents/**/*.md` + `./agents/*.md` — プロジェクトローカルのエージェント（両方の深さ）
2. `~/.claude/agents/**/*.md` + `~/.claude/agents/*.md` — グローバルエージェント（両方の深さ）

すべての場所の結果はマージされ、エージェント名で重複排除されます。同じ名前のグローバルエージェントよりも、プロジェクトローカルのエージェントが優先されます。ユーザーが指定した場合は、代わりにカスタムパスを使用できます。

## 仕組み

### ステップ1: 利用可能なエージェントを発見する

上記の探索順でエージェントディレクトリをGlobします。READMEファイルは除外します。見つかった各ファイルについて:
- **サブディレクトリレイアウト:** 親フォルダ名からドメインを抽出
- **フラットレイアウト:** すべてのファイル名プレフィックス（最初の `-` より前のテキスト）を収集。2つ以上のファイルに現れるプレフィックスだけがドメインとして扱われます（例：`engineering-security-engineer.md` と `engineering-software-architect.md` はどちらも `engineering` で始まる → Engineeringドメイン）。一意のプレフィックスを持つファイル（例：`code-reviewer.md`、`tdd-guide.md`）は「General」にグループ化
- 最初の `# 見出し` からエージェント名を抽出。見出しがない場合はファイル名から派生（`.md`を除去、ハイフンをスペースに置換、title-case）
- 見出し後の最初の段落から1行の要約を抽出

すべての場所を探索してもエージェントファイルが見つからない場合は、ユーザーに「エージェントファイルが見つかりません。確認済み: [探索したパス一覧]。想定: いずれかのディレクトリ内のMarkdownファイル。」と伝えて停止します。

### ステップ2: ドメインメニューを表示する

```
利用可能なエージェントドメイン:
1. Engineering — Software Architect, Security Engineer
2. Marketing — SEO Specialist
3. Sales — Discovery Coach, Outbound Strategist

ドメインを選ぶか、特定のエージェント名を指定してください（例: "1,3" または "security + seo"）:
```

- エージェントが0件のドメイン（空ディレクトリ）はスキップ
- ドメインごとのエージェント数を表示

### ステップ3: 選択を処理する

柔軟な入力を受け付けます。
- 数字: "1,3" はEngineeringとSalesの全エージェントを選択
- 名前: "security + seo" は発見済みエージェントにファジーマッチ
- "all from engineering" はそのドメイン内の全エージェントを選択

5件を超えるエージェントが選択された場合は、アルファベット順に一覧表示し、ユーザーに絞り込みを依頼します。「N件のエージェントを選択しました（最大5件）。残すものを選ぶか、アルファベット順の先頭5件を使う場合は 'first 5' と言ってください。」

選択を確認します。
```
選択済み: Security Engineer + SEO Specialist
何に取り組ませますか?（タスクを説明してください）:
```

### ステップ4: エージェントを並列起動する

1. 選択された各エージェントのMarkdownファイルを読む
2. タスク説明がまだ提供されていなければ入力を促す
3. Agentツールを使ってすべてのエージェントを並列起動:
   - `subagent_type: "general-purpose"`
   - `prompt: "{エージェントファイル内容}\n\nTask: {タスク説明}"`
   - 各エージェントは独立して実行 — エージェント間通信は不要
4. エージェントが失敗した場合（エラー、タイムアウト、空出力）、その失敗をインラインで記録し（例: "Security Engineer: 失敗 — [理由]"）、成功したエージェントの結果で続行

### ステップ5: 結果を統合する

すべての出力を収集し、統合レポートを提示します。
- エージェントごとにグループ化された結果
- 以下を強調する統合セクション:
  - エージェント間の合意点
  - 推奨事項間の衝突や緊張関係
  - 推奨される次のステップ

1件のエージェントだけが選択された場合は統合をスキップし、出力を直接提示します。

## ルール

- **動的発見のみ。** エージェント一覧をハードコードしない。ディレクトリ内の新規ファイルは自動的にメニューに表示される。
- **1チーム最大5エージェント。** 5件を超えるとリターンが逓減し、トークン使用量が過大になる。選択時に強制する。
- **並列ディスパッチ。** すべてのエージェントを同時に実行する — Agentツールの並列呼び出しパターンを使用する。
- **TeamCreateではなく並列Agent呼び出し。** このスキルは独立作業のために並列Agentツール呼び出しを使用する。TeamCreate（マルチエージェント対話用のClaude Codeツール）は、エージェント同士が議論または応答し合う必要がある場合にのみ必要。

## 例

```
ユーザー: team builder

Claude:
利用可能なエージェントドメイン:
1. Engineering (2) — Software Architect, Security Engineer
2. Marketing (1) — SEO Specialist
3. Sales (4) — Discovery Coach, Outbound Strategist, Proposal Strategist, Sales Engineer
4. Support (1) — Executive Summary

ドメインを選ぶか、特定のエージェント名を指定してください:

ユーザー: security + seo

Claude:
選択済み: Security Engineer + SEO Specialist
何に取り組ませますか?

ユーザー: ローンチ前にNext.jsのECサイトをレビューして

[両方のエージェントが並列起動し、それぞれの専門性をコードベースに適用]

Claude:
## Security Engineer の発見事項
- [発見事項...]

## SEO Specialist の発見事項
- [発見事項...]

## 統合
両エージェントの合意点: [...]
緊張関係: Securityはinline stylesをブロックするCSPを推奨し、SEOはinline schema markupを必要としている。解決策: [...]
次のステップ: [...]
```
