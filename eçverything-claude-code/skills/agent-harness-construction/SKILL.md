# エージェントハーネス構築

エージェントが計画し、ツールを呼び出し、エラーから回復し、完了へ収束する方法を改善するときに、このスキルを使用します。

## コアモデル

エージェントの出力品質は以下によって制約されます:
1. アクション空間の品質
2. 観測の品質
3. 回復の品質
4. コンテキスト予算の品質

## アクション空間設計

1. 安定した明示的なツール名を使用する。
2. 入力はスキーマファーストで狭く保つ。
3. 決定論的な出力形状を返す。
4. 分離が不可能な場合を除き、何でも受けるツールは避ける。

## 粒度ルール

- 高リスク操作（deploy、migration、permissions）にはマイクロツールを使用する。
- 一般的な編集/読み取り/検索ループには中粒度ツールを使用する。
- 往復オーバーヘッドが支配的なコストである場合にのみマクロツールを使用する。

## 観測設計

すべてのツール応答には以下を含めるべきです:
- `status`: success|warning|error
- `summary`: 1行の結果
- `next_actions`: 実行可能なフォローアップ
- `artifacts`: ファイルパス / ID

## エラー回復契約

すべてのエラーパスに以下を含めます:
- 根本原因のヒント
- 安全なリトライ手順
- 明示的な停止条件

## コンテキスト予算管理

1. system promptは最小限かつ不変に保つ。
2. 大きなガイダンスはオンデマンドで読み込むskillsへ移す。
3. 長い文書をインライン化するより、ファイルへの参照を優先する。
4. 任意のトークン閾値ではなく、フェーズ境界でcompactする。

## アーキテクチャパターンのガイダンス

- ReAct: 経路が不確実な探索的タスクに最適。
- Function-calling: 構造化された決定論的フローに最適。
- Hybrid（推奨）: ReActによる計画 + 型付きツール実行。

## ベンチマーク

追跡するもの:
- 完了率
- タスクごとのリトライ数
- pass@1 と pass@3
- 成功タスクあたりのコスト

## アンチパターン

- 意味が重複するツールが多すぎる。
- 回復ヒントのない不透明なツール出力。
- 次のステップがないエラーのみの出力。
- 無関係な参照によるコンテキスト過負荷。
